# Build, packaging, processes and shells

Full notes moved out of `AGENTS.md` so they are read on demand, not loaded
into every session. Text is verbatim; the index lives in `AGENTS.md`.

## 2026-07-29 — `npm install <package>` breaks terminals; `npm install` with no args does not. npm strips the executable bit…

2026-07-29: **`npm install <package>` breaks terminals; `npm install` with no args does not.** npm strips the executable bit off files inside a package (it only preserves it for declared `bin` entries), and node-pty's prebuilt `spawn-helper` needs it — without it `terminal:create` dies with `posix_spawnp failed`. The repo's root `postinstall` (`chmod +x node_modules/node-pty/prebuilds/*/spawn-helper`) repairs this, but it **only runs on a bare `npm install`**. A targeted `npm install <pkg>` re-extracts node-pty, re-strips the bit, and skips the root `postinstall` — verified both ways, including an install that reported "up to date" and still broke it. **After adding any dependency, run `npm run postinstall`.**

## 2026-07-29 — A missing runtime dependency produces a build that succeeds and an app that dies on launch. electron-vite…

2026-07-29: **A missing runtime dependency produces a build that succeeds and an app that dies on launch.** electron-vite leaves `dependencies` as bare `import`s in `out/main/index.js` (it never bundles or resolves them), and electron-builder copies prod deps out of `node_modules` — so a package listed in `package.json`/`package-lock.json` but absent from `node_modules` is silently skipped by *both*, and the packaged app throws `ERR_MODULE_NOT_FOUND` at startup. This is what a pull that adds a dep looks like when `npm install` wasn't re-run (it bit `@deepgram/sdk` after the Deepgram merge). **Run `npm install` after any pull/merge that touches `package.json`**, and if a packaged build reports a missing module, check `node_modules/<pkg>` before suspecting the packaging config.

## 2026-07-30 — Distribution is build-from-source on purpose, and the packaging tolerates a missing sidecar. The app is…

2026-07-30: **Distribution is build-from-source on purpose, and the packaging tolerates a missing sidecar.** The app is ad-hoc signed (`identity: null`), so a *locally built* app opens cleanly while the same bundle moved over any network gets `com.apple.quarantine` and macOS rejects an ad-hoc-signed quarantined app with **"Chewo is damaged and can't be opened"** — not the softer "unidentified developer" prompt. That's why the README sends people to `npm run dist:install` rather than a download; `npm run dist:zip` exists for handing someone a build, and it always needs `xattr -dr com.apple.quarantine` on the other end. Only a Developer ID cert + notarization actually fixes this. Two things that make a first build survive: (1) `ensure:stt` is `--soft` everywhere now (`predev`, `predist`, `predist:zip`) because **electron-builder logs `file source doesn't exist` and skips a missing `extraResources` entry rather than failing** (`copyFiles` in `app-builder-lib/out/fileMatcher.js`) — verified by building with the sidecar moved aside, which produced a working app with only `chewo-mcp.cjs` in `Resources/bin/`. So no Swift toolchain costs you dictation, not the build. (2) `dist:install` is `scripts/install-app.mjs`, not a `ditto` one-liner: electron-builder names its output dir per arch (`mac-arm64` vs `mac`), and it refuses to copy over a **running** Chewo, which otherwise leaves a half-replaced bundle that crashes on next launch.

## 2026-07-30 — Never hand-edit a `version` field — releases go through `npm version <patch|minor|major>`. That one command…

2026-07-30: **Never hand-edit a `version` field — releases go through `npm version <patch|minor|major>`.** That one command bumps the root, runs `scripts/sync-version.mjs` from the `version` lifecycle hook to propagate the number into every workspace package, stages them, and lets npm make **one** commit and tag covering all of it; `preversion` gates on `typecheck` + `test`, `postversion` pushes `main --follow-tags`. The `version` hook (not `postversion`) is load-bearing: it fires after the root bump but before the commit, which is the only window where staged files still land inside the tagged commit. `sync-version.mjs` hardcodes its workspace list — extend it when `packages/*` grows. Also worth knowing before adding version ceremony: **semver is not how Chewo identifies a build.** `src/main/app-version.ts` stamps each build with its git commit (`__BUILD_HASH__` from `electron.vite.config.ts`), diffs it against repo HEAD, and drives the sidebar's "behind by N commits" + rebuild CTA — so the version field only surfaces in the .app's Get Info panel and electron-builder artifact names.

## 2026-08-03 — The in-app Update quits before it installs — `dist:install` can never run from inside the app.…

2026-08-03: **The in-app Update quits before it installs — `dist:install` can never run from inside the app.** `runSelfUpdate` used to shell `npm run dist:install`, whose last step is `scripts/install-app.mjs`, which dies on `pgrep -x Chewo` ("Chewo is running — quit it"). The updater *is* Chewo, so the button burned a full electron-builder run and then failed, every time, with the reason visible only in the footer's `title` tooltip. It now runs `npm run dist` and hands the swap to a **detached** `install-app.mjs --wait-for <pid> --reopen` (`detached: true` + `unref()`, output appended to `~/.chewo/update.log` — the only record once the app is gone), then `app.exit(0)` with **no `app.relaunch()`**: the helper reopens the new bundle after the swap, and relaunching here would race it into the old one. Three things the helper has to get right. (1) `pgrep -x Chewo` **also matches Electron's own GPU and utility children** — they exec the same `Contents/MacOS/Chewo` binary — so the post-exit check polls for up to 20 s instead of failing on the first read, which would abort good updates at random. (2) The copy is **staged** (`ditto` → `Chewo.app.incoming`, `mv` target → `.previous`, `mv` staged → target, restoring on failure): the slow failure-prone step happens while the installed app is still intact, and the swap is two same-volume renames. (3) `--reopen` also fires from `die()`, because a failure that happens *after* the app quit must still put something on screen. Unrelated but worth not chasing: `codesign -v --deep --strict` reports "code has no resources but signature indicates they must be present" on the installed app *and* the fresh `dist/` build — pre-existing `identity: null` ad-hoc signing, not something the swap introduces.

## 2026-08-03 — `pgrep -x Chewo` does not find Chewo — it finds the MCP servers, which outlive it. `packages/chewo-mcp` is…

2026-08-03: **`pgrep -x Chewo` does not find Chewo — it finds the MCP servers, which outlive it.** `packages/chewo-mcp` is registered as *Chewo's own binary* under `ELECTRON_RUN_AS_NODE`, so every MCP server a CLI agent spawns is another `MacOS/Chewo` process; they are children of `claude -p`, not of the app, and one observed here had been alive for 30 minutes across two app restarts. Measured 2026-08-03: `pgrep -x Chewo` returned **5 pids, all of them sidecars, and not the GUI process** — so `install-app.mjs`'s running-app guard was inverted in both directions, blocking every in-app Update (`❌ Another Chewo is running`) while never detecting the app it exists to protect. The test is now an exact match on `<bundle>/Contents/MacOS/Chewo` **with no arguments**: sidecars carry the server script as argv[1], and Electron's GPU/utility/renderer children live under `Frameworks/` and carry `--type=`. What made this cost two 15-minute rebuilds to notice: **the helper runs after the app has quit, so its failures had nowhere to report** — the reopened app just showed "New version available" again, which is indistinguishable from the button doing nothing, and the only record was `~/.chewo/update.log`. `die()` now leaves the reason in `~/.chewo/update-error.txt`, which `getVersionStatus` reads on the next launch and reports as `update-failed` (cleared on a successful install, when pressing Update, and whenever the build hash catches up to HEAD). Related: the updater reads `scripts/install-app.mjs` from `__REPO_PATH__`'s **working tree**, not from the installed bundle — so a fix to it only takes effect once it is on the main checkout's branch, not when the new build lands.

## 2026-08-03 — The play button follows the focused session's checkout. `runStartCommands` in `App.tsx` resolves the cwd from…

2026-08-03: **The play button follows the focused session's checkout.** `runStartCommands` in `App.tsx` resolves the cwd from `activeTab`: an isolated, non-pending tab belonging to that project runs the start command in its worktree (`worktreeId` tagged on the pane, so `tabTitle` reports the branch and the strip label carries the `⎇` marker), everything else falls back to `project.path`. This narrows the earlier "dev servers, the play button and the `+` shell always stay in the main checkout" rule — only the `+` shell does now. Two consequences that are choices, not oversights: **ports are not remapped**, so two branches on the same dev port collide rather than one silently serving the other's build; and a run pane counts as a live pane on that worktree, which **blocks `reapMerged`** — an unattended `npm run dev` keeps a merged branch's checkout around, which beats deleting a checkout out from under a running server. A **pending** tab is excluded deliberately: it has no checkout of its own and is only borrowing the shared one, the same reason `pendingBase` hides Update and Ship.

## 2026-08-03 — `+` asks which checkout; ▷ does not. A shell is where you check a branch by hand, and the answer is genuinely…

2026-08-03: **`+` asks which checkout; ▷ does not.** A shell is where you check a branch by hand, and the answer is genuinely per command — `git log`/`npm test` want the session's worktree, `npm install` usually wants main — so `+` opens a two-item `ContextMenu` (the existing `ui/ContextMenu` primitive, anchored at the button's bottom-left; it already portals, clamps to the viewport and handles Escape/outside-click, so no new menu component was written) whenever the focused pane has a worktree, and stays a single click when it does not. ▷ has one obvious answer — the thing you are looking at — so it just follows the focus. Both tag the pane with `worktreeId`, which is what gives it the `⎇` label and the branch in `tabTitle`, and which counts the branch as live against `reapMerged`.

## 2026-08-13 — A link in a chat reply used to eat the app — the main window had no navigation guard at all. `createWindow`…

2026-08-13: **A link in a chat reply used to eat the app — the main window had no navigation guard at all.** `createWindow` set neither `will-navigate` nor `setWindowOpenHandler`, and none of the five `ReactMarkdown` sites overrode `a`, so markdown emitted a plain `<a href>` and clicking one navigated the BrowserWindow itself. With `titleBarStyle: 'hiddenInset'` there is no back button and no close: the page sat on top of the whole UI until ⌘R. The `open-external` IPC had existed the whole time and had exactly **one** caller (the Ship toast's "Open PR"). Fixed in two layers, and both earn their place: `MD_LINKS` (`src/renderer/src/markdownLinks.tsx`) answers the click so no navigation ever starts, and main pins the frame as the backstop for everything markdown is not. Three traps in the backstop. (1) **The one navigation that must survive is the renderer reloading itself** — ⌘R and Vite's HMR full reload are renderer-initiated and come through `will-navigate`, so a blanket deny bricks dev; it is a whitelist of the page we loaded. (2) That whitelist cannot be `startsWith('file://')`, which was the first draft and would have let `[x](file:///…)` navigate a *packaged* build after all — dev matches the server by origin (its URL carries HMR query strings), prod compares against `pathToFileURL(...index.html)` with the query/hash stripped. (3) `openInBrowser` is http(s)-only for the reason the old IPC comment gave: any other scheme hands the OS a string that launches an application of its own choosing, and these strings come from model output. Considered and not built: an in-app browser pane (a `WebContentsView` pane mode beside `chat`/`terminal`) — the default browser is where a link belongs, and that pane is a real build with its own sizing, chrome and security policy.

## 2026-08-24 — Driving the app with `npx electron out/main/index.js` writes to `Application Support/Electron-dev`, not to…

2026-08-24: **Driving the app with `npx electron out/main/index.js` writes to `Application Support/Electron-dev`, not to the installed app's store — but the installed app's own store is `Application Support/chewo`, lowercase, and macOS is case-insensitive.** So the earlier "dev and packaged builds keep separate `projects.json` files" is true, and this is *why*: a bare `electron <entry>` run takes Electron's own app name, not the one in `package.json`. Two things follow for anyone screenshotting a UI change over CDP. (1) You can click through Settings freely — theme changes, added projects, cleared project lists all land in `Electron-dev` and the user's real Chewo never sees them; there is a stale `chewo-dev` directory from an older convention that nothing writes to any more. (2) That also means **the dev instance does not reproduce the user's own settings**, so "it looks right here" is a statement about the defaults, not about what they will see — check their `settings.json` before claiming a themed change reaches them. Verified by mtime and by reading all three files while the packaged app was live.

## 2026-08-31 — A shell's scrollback lives in its xterm and nowhere else, so a terminal pane may never be unmounted — and the…

2026-08-31: **A shell's scrollback lives in its xterm and nowhere else, so a terminal pane may never be unmounted — and the pane must not be the element FitAddon measures.** Three fixes to the shell tool, each with a rule behind it. (1) **`+` follows the focused session's checkout now, like ▷ does**, reversing the 2026-08-03 "`+` asks which checkout" entry: the menu was two clicks on every shell for a question whose answer is the session you are looking at almost every time. The other answer (`npm install` usually wants main) is still there on **right-click** of New shell, and the button's tooltip names the checkout the click will use. (2) The tools column was gated on `workflow === 'code' && activeTool`, so leaving Code for Notes or Todo — or just opening Files — unmounted `TerminalPane`, which calls `term.dispose()`. **Main does not buffer pty output** (`proc.onData` → `safeSend`, no replay), so every byte written before the next mount is gone for good and the shell comes back blank. The column now stays mounted whenever any shell is open and is hidden with `.tools-column--hidden`; `ShellWorkspace` takes `panes` (every project's shells, mounted, `display:none` when not the active tab) separately from `tabs` (the selected project's, which is what the tab bar lists), so switching projects no longer costs a terminal its output either. Files and Git still mount only when chosen, so nothing new watches the filesystem from inside Notes. (3) **`.terminal-pane` is `box-sizing: content-box`, and that is load-bearing.** FitAddon sizes the terminal from `getComputedStyle(container).height` minus the padding declared on `.xterm` itself — under the app-wide border-box the container reports its *padded* height, so an 8px gutter bought a row that did not fit: measured 55 rows × 15px = 825px inside 812px of room, with the last line clipped off the bottom of the window and the same overflow on the right. content-box makes the computed height the content height (812 → 54 rows) and the gutter stays painted by the pane's own background. **Moving the padding onto `.xterm` instead does not work**: `.xterm-viewport` is absolutely positioned and so ignores it, painting xterm.css's black `#000` over the gutter — tried, screenshotted, reverted. Found on the way and fixed: `channelFanout` in `src/preload/index.ts` iterated its subscriber Set with no try/catch, so **one throwing subscriber silently blanked every pane that subscribed after it** — verified live, a new shell rendered nothing at all with no error near it.

## 2026-09-18 — Killing a pane killed one process and orphaned everything beneath it. `killTerminal` was `proc.kill()` and…

2026-09-18: **Killing a pane killed one process and orphaned everything beneath it.** `killTerminal` was `proc.kill()` and `killChat` was `record.proc.kill()`, so a pane's grandchildren survived the pane, the project and the app — found by tracing a machine burning ~700% CPU to **eight `while :; do :; done` subshells running for sixteen days**, spawned by an agent's own flaky-test script (`/tmp/loadflake.sh`, in an Argo session) that backgrounded them with `&` and put `kill $hogs` on its last line. That line never ran: the script was a *background* Bash task, the session ended mid-loop about 54 minutes in, and the already-detached loops were adopted by launchd. The chain is four deep — Chewo → a `claude` pane → the CLI's own background task → the hogs — so nothing Chewo killed was ever their parent. `src/main/process-tree.ts` now sweeps descendants **before** the pane's own process dies, which is the only window there is: once the parent exits, a reparented process keeps no record of who started it and the tree is unrecoverable. Five things it has to get right. (1) **Deepest-first ordering**, or signalling a middle process lets its own children reparent and escape the same sweep. (2) The roots are **excluded** — node-pty and `child_process` each have a `kill()` that does more than a bare signal (closing the pty, ending stdin), so they stay in charge of their own process and only the descendants are signalled by pid. (3) The `ps` read is **synchronous**, because `disposeAll*` runs inside the quit path where a promise has no guarantee of settling; it costs ~10ms, and `immediate: true` there skips the grace period since there is no later tick to run the follow-up sweep in. (4) The SIGKILL follow-up **re-reads the table** rather than blanket-killing the original list, so a pid recycled onto an unrelated process in those 1.5s is not hit; a cycle guard and a `pid <= 1 || pid === process.pid` filter exist because a malformed table must not be able to turn this into a self-kill. (5) **A child that calls `setsid` is already an orphan before we look** and cannot be caught this way — which is also true of the loops above, since they were orphaned when the *task* died, long before the pane closed. So this narrows the leak without closing it: the remaining half is an orphan sweep that surfaces PPID-1 processes under a known project path, deliberately with a button rather than an automatic kill, since "was this ours" is only ever a heuristic after reparenting. Verified by a live probe both ways — a shell that backgrounds three spin loops leaves all three running under a bare `proc.kill()` and none under the new path.

## 2026-09-18 — A shell belongs to the session it was opened from, and closing that session takes it down. Shells were pooled…

2026-09-18: **A shell belongs to the session it was opened from, and closing that session takes it down.** Shells were pooled per project, so two sessions on two branches shared one tab bar and running the tests for one meant picking the right tab by hand. `TerminalTab.ownerPaneId` names the owning agent pane; `visibleShells` (`src/renderer/src/shellScope.ts`, pure and tested like `tabStrip.ts`) shows the focused session its own shells plus the project's **unowned** ones — a shell opened with nothing focused stays a project shell, because hiding a running process behind a focus change with nothing to say where it went is worse than a slightly wider list. Four things hold it together. (1) **`replacePane` re-points `ownerPaneId`**, or a pending session that cuts a worktree on its first message orphans its shells on an id that no longer exists. (2) A new shell follows the *owner's* project, never `selectedProject`: the two can differ, and a shell filed under one project while standing in another's checkout is a trap — it would also survive the wrong `deleteProject`. (3) **Busy is "the pty has a child"** — `rootsWithDescendants` in `process-tree.ts` → `busyTerminals` → `terminal:busy` → `api.termBusy`. An idle zsh sits at its prompt with no children, one running `npm run dev` has the server beneath it, so the close confirm names only the shells actually doing something; verified live over CDP, and accepting killed the pty, `npm run dev` and the electron-vite child together through the existing descendant sweep. Same blind spot as that sweep: a child that called `setsid` is already out of the tree. (4) The confirm is only on **session** close, not on a shell tab's own X — that X is already an explicit act on that one shell. Related move: **▷ left the sidebar's project row for the session header beside Ship** (`components/RunButton.tsx`, ⌘⇧P). Its scope was always the focused session's checkout, which a project row cannot show — the same glyph did two different things depending on what was focused elsewhere — and the shells it opens are now owned by that session. ⌘⇧P guards `e.repeat` (a toggle bound to keydown fires once per repeat, so holding it opened a shell a frame) and reaches the run through a ref, since the listener is registered once and its closure would hold whichever session was focused then. ⌘P without shift is still dictation, and xterm passes other ⌘ combos through, so it works with terminal focus like ⌘⇧E/⌘⇧B. The confirm itself is the app's own dialog, not `window.confirm`: `components/ConfirmDialog.tsx` over `ModalShell`, driven by `askConfirm` in App, which returns a promise the buttons resolve so a caller reads exactly like the native one — Escape, the backdrop and the close button all mean no. The native sheet rendered in the system font at the system size and flattened every question into OK/Cancel however specific the act was; here the button says what it does (*Close and stop it*). **The other two `window.confirm` sites — discarding a change and removing a worktree — are deliberately still native**, since the worktree one chains a second confirm on git's refusal and converting it blind would touch a destructive path nobody asked about.
