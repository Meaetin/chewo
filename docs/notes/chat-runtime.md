# Chat panes and the CLI wire format

Full notes moved out of `AGENTS.md` so they are read on demand, not loaded
into every session. Text is verbatim; the index lives in `AGENTS.md`.

## 2026-08-25 — Codex chat parity has two inputs: live app-server items and resumed rollout history. Codex 0.144 rollouts…

2026-08-25: **Codex chat parity has two inputs: live app-server items and resumed rollout history.** Codex 0.144 rollouts record harness activity as `custom_tool_call` / `custom_tool_call_output`, with an `exec` wrapper whose JavaScript invokes the real operation (`tools.exec_command`, `tools.apply_patch`, etc.); older 0.142 files use `function_call` / `local_shell_call`. `parseCodexSession` must preserve both generations and seed structured tool input/display names, or a resumed Codex pane renders assistant prose but silently drops every command and edited file even though the live app-server UI works.

## 2026-08-02 — Chat panes and terminal panes are two runtimes for one thing, sharing one id space. A `TerminalTab.mode` of…

2026-08-02: **Chat panes and terminal panes are two runtimes for one thing, sharing one id space.** A `TerminalTab.mode` of `'chat'` drives the agent over JSON (`src/main/chat-sessions.ts` → `ChatPane`); `'terminal'` is the pty. Ids come from `src/main/pane-ids.ts` so the tab strip, drag/drop, `paneTabs` and `MainView` never learn the difference — which is also what lets a conversation move between the two by killing one and `--resume`-ing the same `sessionId` in the other. **The terminal is not going away**: shell panes (`npm run dev`, worktree setup, the play button) are ptys forever, so "replace the TUI" would delete the fallback while keeping all the machinery. **Removed 2026-08-03: the chat pane's header** (agent badge, model, cwd, and the "Terminal" button that handed a conversation to a pty). The cwd duplicated the tab's ⎇ label and the branch chip, and a whole bar's height for an escape hatch that was never used did not earn it. `openInTerminal` went with it — the `--resume` ids still line up, so the swap is a caller away, but there is no UI for it and `claude auth` / an interactive `/config` / a broken wire format now need a shell pane. Four things about the Claude wire format cost real time to find, all verified against CLI 2.1.220 by `npm run canary:chat` (run it after every CLI update): (1) **`--permission-prompt-tool stdio` is undocumented** — absent from `claude --help` — and it is the *only* way to get permission prompts as `can_use_tool` control requests; `--permission-mode manual` just fails the tool with "you haven't granted it yet" and never asks. (2) Echoing the CLI's own `permission_suggestions` back as `updatedPermissions` is what makes "always allow" stick, so the CLI owns that state and we keep no shadow allowlist. (3) **Assistant text arrives by two routes** — as `stream_event` deltas *and* again in the completed `assistant` message — except locally-handled slash commands (`/context`), which only ever produce the `assistant` message; rendering both duplicates every reply, rendering one loses half, so `claude-chat.ts` tracks which message ids streamed. Block indices restart at 0 per message, so block ids must be `messageId:index`. (4) **`system/init` is withheld until the first turn begins**, so a fresh pane has no model and no slash commands until you have already sent something — the fix is the SDK-style `initialize` control request at spawn, which returns the full command catalog immediately. Related trap: `createChat` returns through IPC *before* the renderer mounts the pane, so nothing may be emitted synchronously from it (that event has no listener yet) — spawn-time facts like cwd reach `ChatPane` as props.

## 2026-08-02 — Whether a thinking block has readable text is per-model, and streaming cadence needs smoothing. Verified…

2026-08-02: **Whether a thinking block has readable text is per-model, and streaming cadence needs smoothing.** Verified 2026-08-02: haiku streams reasoning as `thinking_delta`s, but **opus emits the thinking block and a `signature_delta` and nothing else** — zero deltas, zero characters in the final `assistant` echo, because the reasoning is encrypted. So a thinking disclosure must check for text before offering a chevron, or it opens onto nothing (`chat-thinking-head--static` in `ChatItems.tsx`). Two neighbouring UI facts. (1) The CLI reports an **interrupted turn exactly like a failed one** (`result` with `is_error`), so `chat-sessions.ts` sets a `interrupted` flag in `interruptChat` and stamps `stats.cancelled` on the turn it stops — otherwise stopping on purpose reads as "The turn ended with an error". A tool in flight when a turn ends never receives its `tool_result`, so `reduceChat` settles any still-`running`/`awaiting` chip to `cancelled` or it spins forever. (2) Model text arrives in bursts of roughly a clause, which reads as stuttering; `useSmoothText` reveals it a few characters per frame with the step derived from the backlog, so it always catches up and never becomes the bottleneck. It snaps to full text under `prefers-reduced-motion` **and when the page is not visible** — Chromium throttles rAF for hidden windows, which would otherwise leave text stranded behind. The streaming caret is appended to the markdown *source*; as a sibling element it lands after the trailing `<p>` and sits on its own line.

## 2026-08-02 — Resuming replays nothing, and the transcript parser was silently truncating long sessions. `claude --resume…

2026-08-02: **Resuming replays nothing, and the transcript parser was silently truncating long sessions.** `claude --resume <id>` loads the conversation into the CLI's own context and then stays quiet until the next turn — no history crosses the wire — so a resumed chat pane opens blank. It is seeded from disk instead (`seedItems` in `agent-chat.ts`, fed by the same `getSession` parse the transcript view uses), from `TerminalTab.resumeSessionId` — deliberately *not* `sessionId`, which a fresh pane fills in itself and would make every live message render twice. Finding that exposed a **pre-existing adapter bug**: `parseClaudeSession` linearised by walking `parentUuid` from the newest record, but compaction and summary boundaries re-point or drop that link, and *every boundary severs the chain*. On a real long session, 964 main records yielded a **16-record chain across 58 breaks** — so both the chat pane and `TranscriptView` showed the last handful of messages and nothing else, while `meta.messageCount` (computed over the whole timeline, so unaffected) cheerfully said 488. The parse now uses the chain only when it actually reaches the first record and otherwise falls back to append order, trading rewind-branch pruning for completeness in exactly the case where the links are too broken to prune by; `tests/fixtures/claude/v2.1-compacted.jsonl` pins it. Related: the CLI withholds `system/init` until the first turn, so a pane's **model is unknown until the user speaks** — the header shows nothing rather than an indefinite "Starting…", which reads as a pane that never loaded, and the "Terminal" escape hatch falls back to the resume id so it is not dead on a resumed pane.

## 2026-08-02 — Clicking a session in the sidebar resumes it — there is no read-only transcript any more. `TranscriptView` is…

2026-08-02: **Clicking a session in the sidebar resumes it — there is no read-only transcript any more.** `TranscriptView` is deleted; `openSession` focuses the existing pane if the session is already running, otherwise calls `resumeSession`, which opens a chat pane seeded with the history. A running session's row is **dimmed** (`.session-row--running`) rather than disabled, because the useful action is still "focus that pane" — what must never happen is a second process starting on a conversation that is already live, which interleaves the file and makes the next resume pick the wrong branch. Find-in-conversation moved with it: `components/chat/FindBar.tsx` keeps ⌘F, and it paints matches with the **CSS Custom Highlight API** rather than wrapping text in `<mark>`s — the thread is live markdown that re-renders on every token, so mutating it to insert elements would fight the reconciler; ranges over text nodes survive re-render. Its Escape handler is registered in the **capture** phase so closing the find bar does not also fire the pane's Escape-to-interrupt. Two classes survive the deletion and must not be swept up as dead: `.message-markdown` (the chat thread uses it, so a live reply and a re-read one look identical) and `.transcript-error` / `.transcript-loading` (reused by `CapabilitiesView`). Open perf question, not yet a bug: a resumed pane renders every message — 539 items and ~29,000px on a real session — so a long conversation will want virtualisation before this grows.

## 2026-08-02 — A resumed pane renders one page and grows upward; the tab bar's `+` is a shell, nothing else. Seeding a long…

2026-08-02: **A resumed pane renders one page and grows upward; the tab bar's `+` is a shell, nothing else.** Seeding a long conversation whole cost ~29,000px of DOM (539 items), so `ChatPane` withholds all but the last `PAGE` (50) and pulls earlier ones in as the user scrolls near the top — 51 items and ~2,800px on the same session. The window is tracked as a **`hidden` count from the front**, not a visible count: new items append at the end and are always shown, so nothing scrolls out of view above while the agent is talking. Two scroll subtleties, both bugs before they were fixed. (1) Prepending pushes content down, so the restore anchors on the distance from the *bottom*, and that effect is declared **before** the recorder so it consumes the gap measured on the previous render. (2) Pinning to the bottom only when items change is not enough — **markdown finishes laying out after that effect runs**, growing the scroll height underneath it and leaving a resumed pane a screen short of the newest message; the pin re-asserts on *every* render instead, which also follows the stream. ⌘F expands the window to everything first (`FindBar`'s `onOpen`), because find walks the DOM and would otherwise silently search one page. Separately, the `+` in the tab bar creates a shell directly — no menu. Agents are created from the sidebar's "New session", which already offers both CLIs, and having two launchers meant two things to keep in sync.

## 2026-08-03 — A session is created undecided, and nothing is spawned until the first message. `selectSection` opens an…

2026-08-03: **A session is created undecided, and nothing is spawned until the first message.** `selectSection` opens an unstarted pane when the section has no tabs, and the sidebar's "New session" does the same; the menu that used to ask for the agent and the checkout up front is gone, and so is `startIsolatedNow`. An unstarted pane is `TerminalTab.pending`: a real tab with a composer and **no process behind it**, whose id comes from `pane:reserve` (the same `nextPaneId` counter, so the pane it becomes can take its place in the strip). Everything the setup row asks — agent, model, effort, checkout — is only answerable once you know the task, and a CLI spawned before those were settled would have to be killed and respawned on each change; `startChosenSession` builds the real pane on the first message and always returns true for a pending tab. Consequences worth knowing. (1) Choosing either agent keeps the same chat runtime; only its main-process transport changes. (2) A pending pane's slash palette is provider-specific: Claude's catalog is read through a throwaway `initialize` handshake, while Codex stays empty because app-server has no TUI command catalog. (3) Pending tabs are never persisted: `savedFor` filters on `!!t.sessionId`. (4) `killPane` on a pending tab calls `chatKill` for an id main has never seen, which is a deliberate no-op.

## 2026-08-03 — Auto-scroll is per pane, and "pinned" is a ref, not state. Every pane stays mounted and is hidden with…

2026-08-03: **Auto-scroll is per pane, and "pinned" is a ref, not state.** Every pane stays mounted and is hidden with `display: none`, which zeroes `scrollHeight`/`clientHeight`/`scrollTop` — and every `ChatPane` re-renders whenever App does. So `ChatPane`'s run-on-every-render pin effect was firing on *hidden* conversations, writing `scrollTop = scrollHeight` = 0 (scrolling them to the top) and recording a bogus bottom-gap: one talking agent visibly moved every other chat. **Every scroll write is now gated on `active && el.clientHeight > 0`**, and the bottom-gap restore also runs on `active` changing, because a pane returning from `display: none` comes back with its offset discarded. The second bug was the stickiness itself: the restore effect had `pinned` in its deps, so scrolling up flipped `pinned` → fired the restore → `scrollTop = bottom - bottomGap`, and the gap last recorded *while pinned* is 0 — **the act of un-pinning was what slammed you back to the bottom**. `pinned` is a plain `useRef` now: nothing renders off it, deps can't fire on it, and it can be cleared synchronously from `onWheel`(deltaY<0)/`onTouchMove` — which is load-bearing during a stream, since a token can re-render between the wheel and the `scroll` event it eventually produces and re-pin under a gesture already in flight. It re-pins only by reaching the bottom again (<60px) or by sending, which is an explicit "move this on".

## 2026-08-03 — The composer accepts pasted images and long text, and the image goes to disk before it goes anywhere else. A…

2026-08-03: **The composer accepts pasted images and long text, and the image goes to disk before it goes anywhere else.** A paste becomes a chip inside the composer pill (`.chat-attachments`, mirroring the setup row along the bottom) when it is an image or text over `PASTE_MIN_LINES`/`PASTE_MIN_CHARS` — a paragraph still pastes as a paragraph. **Verified 2026-08-03 against CLI 2.1.220** with a solid-red probe image: `--input-format stream-json` accepts a *content array* on a user message and the model genuinely sees inline `{type:'image',source:{type:'base64',…}}` blocks (it named the colour), so a chat pane needs no `--add-dir` and no Read call to look at a screenshot. Despite that, every pasted image is still **staged to a file** in `~/.chewo/attachments` the moment it is pasted, because the four ways a message can reach an agent do not agree on how to carry pixels — chat inlines base64, a codex pty takes `-i <file>`, a claude pty reads a path out of the prompt — and a file is the one representation all three derive from. That translation is `openAgent`'s job and nowhere else's; a card run does **not** use it, since `composeCardPrompt` already names its assets (SPEC-TODOS §10.2) and would say it twice. Long text is folded back into the message verbatim inside `<pasted label="…">` tags, so the chip is a display device, not a transformation. Four traps. (1) The bubble must show the chip, not the blob, which is why `deliver` in `ChatPane` takes a `display` *and* a `message` — and why `splitComposed` (the inverse of `composeMessage`) exists at all: a pane replaced on its first message is handed an already-composed prompt and would otherwise render the whole log. (2) `branchNameFor` must be fed that same `display`, or a short sentence lets the slug's five words eat the wrapper tag (`fix-this-pasted-label-text`). (3) `imageBlocks` compares `dirname(resolve(p))` against the staging dir, **not** `startsWith` — a prefix test accepts `<dir>/../../.ssh/id_rsa`. (4) An X placed on `IconButton` cannot be absolutely positioned by its own class: `.tooltip` (the wrapper IconButton renders) is itself `position: relative`, so the offset goes on `.chat-attachment > .tooltip`.

## 2026-08-03 — A tool result carries more than its prose, and the extra is where the UI lives. An Edit's `tool_result` text…

2026-08-03: **A tool result carries more than its prose, and the extra is where the UI lives.** An Edit's `tool_result` text is only "The file … has been updated successfully" — the actual patch rides beside it on `tool_use_result` (live wire) / `toolUseResult` (session file), **the same value shape both ways**, which is why one parser (`src/shared/diff.ts`, `parseToolPatch`) serves `claude-chat.ts` and `adapter/claude.ts` both. Chewo discarded that field, so the chat's edit chip could name a file and nothing else. Shapes, verified against CLI 2.1.220 on 2026-08-03: Edit/MultiEdit give `{filePath, structuredPatch: [{oldStart, oldLines, newStart, newLines, lines}]}`, Read gives `{type:'text', file:{…}}` (no patch), and a **Write that creates a file reports `structuredPatch: []`** — there is no "before" to diff, so its `content` is turned into an all-added hunk rather than rendering as "edited, nothing changed". Three things around it. (1) `tool_use_result` is per *event*, not per content block, so it is only attached when the event carries a single `tool_result` — otherwise there is no saying which file it belongs to. (2) The renderer is the git panel's, extracted to `components/DiffBody.tsx` and its CSS de-prefixed to `.diff-line`/`.diff-ln`/`.diff-code`; a patch is serialized *back* to unified text (`patchToUnified`) rather than rendered from hunks, so an agent's change and the same change read back from `git diff` are one picture with one set of line-number rules. (3) Rows are capped twice and neither cap is silent — 500 at the parser (`ToolPatch.omitted`, since a 5,000-line Write crosses IPC and becomes DOM) and 24 at the chip, which folds behind "Show N more lines"; a diff that quietly stops reads as the whole change.

## 2026-08-03 — `requires_user_interaction` means the approval card *is* the tool's UI — Allow/Deny is the wrong question and…

2026-08-03: **`requires_user_interaction` means the approval card *is* the tool's UI — Allow/Deny is the wrong question and answering is the permission.** The SDK types (`@anthropic-ai/claude-agent-sdk`, `SDKControlPermissionRequest`) define it as "one-tap Approve/Deny must not be offered: the tool's approval card IS the user-interaction surface". Chewo rendered its generic "Allow AskUserQuestion?" card, and allowing ran the tool with no answers — so the model was told **"The user did not answer the questions"** no matter which button was pressed. The answers ride back inside `updatedInput` (`{...input, answers: {…}}`), and two details are load-bearing and neither is guessable: the map is keyed by the **question text**, not the `header` the card displays, and a multi-select answer is **one comma-separated string**, not an array — verified 2026-08-03, a header-keyed or array-valued map echoes into `tool_use_result.answers` and still yields "did not answer". A top-level `response` string also works and *overrides* the map ("The user responded: …"), but it is global rather than per question, so `ask-user-question.ts` does not use it and free text is just another answer string. The card only replaces Allow/Deny when the input actually parses as a question set (`parseAskQuestions` → `null` otherwise), so an unrecognised interactive tool still gets a prompt instead of an empty dialog. `npm run canary:chat` now spends a second haiku turn pinning both this and `structuredPatch`.

## 2026-08-03 — The chat stream carries how full the *context window* is, and nothing about how much of a rate-limit window…

2026-08-03: **The chat stream carries how full the *context window* is, and nothing about how much of a rate-limit window is left.** Verified against CLI 2.1.220 (live probe + stored session logs): the numerator is on every `assistant` message as `message.usage` — and it must be `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`, since a cached token still occupies the window and counting only fresh input reports *8 tokens* for a conversation sitting at 16% (a real turn here reads 32,467 cached against 8 fresh). The denominator appears **once per turn**, in `result.modelUsage[<model>].contextWindow`, so a pane knows the numerator a turn before the denominator — the readout is a token count until the first `result` and a percentage after. A turn that ran subagents lists their models in `modelUsage` and emits *their* `assistant` messages with `parent_tool_use_id` set; both are filtered out, or the reading collapses to a few hundred tokens every time a Task runs. What is **not** available: `rate_limit_event` is the whole story on limits and its `rate_limit_info` is only `{status, resetsAt, rateLimitType, overageStatus, isUsingOverage}` — no utilization, and only the *binding* window (`five_hour` in practice; the CLI also names `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `seven_day_overage_included`). The percentages `/usage` prints come from a separate authenticated `GET /api/oauth/usage` the CLI makes with the user's OAuth token, and **Chewo now makes that call too** (`src/main/claude-usage.ts`) — it is the only source of a "% used" figure, so the alternative was fabricating one. Verified live 2026-08-03: with `authorization: Bearer <accessToken>` + `anthropic-beta: oauth-2025-04-20` it answers with `five_hour` and `seven_day` objects carrying `utilization` (a percentage) and `resets_at` (unix seconds) — the per-model weeklies the CLI names are simply absent when they do not apply. The token is read from the macOS Keychain (`security find-generic-password -s 'Claude Code-credentials'`, falling back to `~/.claude/.credentials.json`), used, and dropped: it is never logged, never cached, and **never crosses IPC** — only parsed percentages reach the renderer. Four rules keep this from becoming a liability. (1) **Every failure returns null** and the composer falls back to naming the window from `rate_limit_event`; nothing in the app ever waits on this call. (2) **We never refresh the token** — an expired one means the readout goes quiet until Claude Code refreshes it itself, because minting tokens against someone else's OAuth client is not our business. (3) The response shape is treated as a suggestion: `parseAccountUsage` walks the whole payload for window-named objects with a numeric utilization rather than reaching down a fixed path, and a 200 it cannot read counts as a *failure*, not as "0% used". (4) Main caches for 60 s and single-flights, so a dozen panes cost one request; the renderer forces a re-read only on the falling edge of `busy`, the one moment the number is known to have moved. **A resumed pane reads the numerator off disk** (`ParseResult.contextTokens`, the newest non-sidechain `assistant` record's own `usage`) because `--resume` replays nothing and the first live reading is a whole turn away — the window's *size* is never written to the session file, so a resumed pane says `Context 214k` until its first reply and a percentage after. `promptTokens` therefore lives in `shared/agent-chat.ts` and is used by both the wire and the parser: the two must agree, or the number visibly jumps the moment the user speaks. Measured on real sessions here, the figure tracks conversation length sensibly (39k over 8 messages, 475k over 400) — the ones above 200k are the `[1m]` Opus sessions, which is exactly why the window is read from `modelUsage` rather than assumed.

## 2026-08-04 — A tool result can be a picture, and the picture is the whole result. A `Read` of a PNG (or an MCP screenshot…

2026-08-04: **A tool result can be a picture, and the picture is the whole result.** A `Read` of a PNG (or an MCP screenshot tool) comes back as a `tool_result` whose content array holds `{type:'image',source:{type:'base64',media_type,data}}` and **no text at all** — so Chewo's old flatten-everything-to-`[${type}]` rule rendered the literal string `[image]` and the chip read as a tool that returned nothing. Verified 2026-08-04 against CLI 2.1.220 on both routes, which carry the identical shape: the live wire (`npm run canary:chat`, third probe — it reads a 1×1 PNG and asserts `tool_result.images`) and the session file (8 Read calls on a real transcript, 250–440 KB of base64 each). One splitter serves both, `splitToolResult` in `src/shared/tool-images.ts`, for the same reason `parseToolPatch` does. Four rules. (1) The media type is **whitelisted** to what an `<img>` paints and the payload is checked as base64, because it lands in a `data:` URL. (2) Nothing is ever dropped silently — an image past a cap leaves a `[image — not shown]` line, since a chip that shows nothing where a picture was is exactly the bug being fixed. (3) A **resumed** pane spends a `SEED_IMAGE_BUDGET` (24 MB of base64) **newest-first**, which is why `collectToolResults` walks records backwards: a session file keeps every screenshot it ever read and a resumed pane holds every item in memory. (4) The chip **auto-opens** on images the way it does on a patch, and the image is capped at 320px with click-to-full-size.

## 2026-08-07 — `TodoWrite` no longer exists — the plan is a `TaskCreate`/`TaskUpdate`/`TaskList` family, and it is folded…

2026-08-07: **`TodoWrite` no longer exists — the plan is a `TaskCreate`/`TaskUpdate`/`TaskList` family, and it is folded into state rather than rendered per chip.** Verified against CLI 2.1.221 by live probe (and pinned by a fourth `npm run canary:chat` turn): the tool list has no `TodoWrite` at all, so anything written from memory against it is inert code that compiles, passes tests and never fires — which is exactly how it was nearly shipped here. The shapes, all on `toolUseResult`: `TaskCreate {subject,description,activeForm?}` → `{task:{id,subject}}`; `TaskUpdate {taskId,status?,owner?,addBlockedBy?}` → `{success,taskId,updatedFields:[…],statusChange?:{from,to}}`; `TaskList {}` → `{tasks:[{id,subject,status,owner?,blockedBy}]}`. Four things follow. (1) **`updatedFields` names what changed but never carries the new value** — only `statusChange` does — so an owner or a blockedBy edge exists solely on the *input*, and `applyTaskResult` takes both halves. The join happens in `reduceChat` (via `callInput`), because the seam where `parseToolPatch` runs has the result but not the call. (2) There is no whole-list write: a plan arrives as N separate creates, so it is accumulated in `ChatState.tasks` and drawn once by `components/chat/TaskPanel.tsx`, with the feeding chips suppressed by `isPlanTool`. That set is **named explicitly and must stay that way — `Task` itself is the subagent launcher**, and `TaskGet`/`TaskOutput`/`TaskStop` are about a running subagent, so a `Task` prefix match would hide real work. (3) `TaskList` is authoritative for everything it reports but **does not echo `activeForm`**, so a reconcile carries it over by id or the running row silently reverts to its imperative subject the moment the agent lists. (4) Resuming replays nothing, so `collectTasks` in `adapter/claude.ts` folds the plan forward out of the session file (forward, not off the newest `TaskList` — most plans are never listed) and `ChatPane` seeds it only when a live turn has not already moved it. `deleted` is a status on the wire but not a state: the schema removes the task, so it leaves the list rather than rendering as a tombstone.

## 2026-08-07 — A per-pane clock must not tick while the pane is hidden. `useElapsed` puts `Working… 1:24` on the chat's…

2026-08-07: **A per-pane clock must not tick while the pane is hidden.** `useElapsed` puts `Working… 1:24` on the chat's working line — "Working…" alone cannot tell three seconds from four minutes, which is the difference between waiting and suspecting a hang. Every `ChatPane` stays mounted under `display: none`, so a 1 Hz timer in each one would re-render every conversation in the window once a second for a number nobody can see; the interval is gated on `active`, and the reading is derived from a start stamp rather than counted, so a pane switched back to is immediately right instead of resuming where it left off. Same family of bug as the scroll-pin one above, and the same fix: gate on `active`. `formatElapsed` lives in `src/renderer/src/elapsed.ts` — DOM-free and tested, like `selectPlacement.ts` and `tabStrip.ts`.

## 2026-08-07 — `AskUserQuestion` is one question per page. The tool takes up to four questions of up to four options each,…

2026-08-07: **`AskUserQuestion` is one question per page.** The tool takes up to four questions of up to four options each, every option can carry a description, and stacked that is a card taller than the window — it read as a wall rather than as a question. `QuestionCard` pages instead, with a dot stepper that fills as each question is answered and is clickable to jump back. Paging is **purely presentational**: `composeAnswers` still receives every pick at once, so the wire contract in `ask-user-question.ts` is untouched. Two rules in the interaction. A single-select pick auto-advances (picking the one answer a question accepts *is* moving on), but multi-select cannot — there is no way to know you are finished — and **the last page never auto-advances into a send**, because the tool result is always an explicit act. And since the question blocking Send can be several pages back, the disabled state names which one.

## 2026-08-25 — Every tool call already carries a sentence saying what it is for, and Chewo was throwing all three of them…

2026-08-25: **Every tool call already carries a sentence saying what it is for, and Chewo was throwing all three of them away.** Three separate defects behind one complaint that the thread reads as a wall of shell syntax. (1) **`Bash` is handed a human-written `description` on every call** ("Lint the new files") — verified across 25 real session files, it is present on every `Bash` and every `Agent` — and `toolSummary` reached for `command` first, so the chip showed the invocation and never the reason. That field is exactly what the Claude desktop app prints. Naming now lives in `shared/tool-label.ts` (`toolLabel` → `{title, detail}`, pure and tested): Bash takes its own description, the file tools get a past-tense verb plus their path, an MCP tool is split out of its `mcp__<server>__<tool>` address, and anything unknown falls back to the CLI's description then to its own name. (2) **`launchedTask` in `subagent.ts` had never been called by anything** — written, tested, and wired to nothing — which is why a dispatch chip rendered the subagent's whole 4 KB brief as its one-line summary. (3) **Expanding a chip showed `call.result` and nothing else**, so on a dispatch the only readable content was the launcher's own metadata ("Async agent launched successfully… do not mention the agentId") and the brief was unreachable from the UI. `toolInputText` renders the input as the thing it is — `$ command`, a subagent's prompt as prose, a Write's content — and it is drawn *above* the result. Two rules it has to keep: an edit that produced a patch shows the patch instead (the patch is a better account of the change than the arguments that asked for it), and a chip that **opened itself** because it holds an image or a diff does not print its arguments unasked, or every screenshot gains a JSON header — expanding it by hand still shows them. **The resumed half needed a fourth fix:** `adapter/claude.ts` set `text: summarizeToolInput(block.input)` and never `toolInput`, so `seedItems` synthesized `{command: m.text}` and a resumed pane could only re-read the gist — every one of the above was live-only until it carried `block.input` through. `adapter/codex.ts` had always set it.

## 2026-08-25 — Consecutive tool calls fold into one row, and what may *not* fold is the whole design. `groupChatItems`…

2026-08-25: **Consecutive tool calls fold into one row, and what may *not* fold is the whole design.** `groupChatItems` (`shared/chat-groups.ts`, pure and tested like `tabStrip.ts`) collects runs of three or more into a `Ran 9 commands` row; `ChatPane` renders `ChatRow`s rather than `ChatItem`s so the decision lives in one testable function instead of in a render loop. Four kinds of call are never swallowed: an `awaiting` one (it is blocking the turn), one carrying a patch or an image (both auto-open, and burying them behind two clicks would undo that), and a failure or denial (that is the outcome you go looking for). Three is the threshold because folding a pair costs a click to read what was already on screen. A group **opens itself while anything inside is running and folds when the run ends** — during a turn the useful reading is what is happening, afterwards it is what was said. Two traps. (1) A plan-tool call (`TaskCreate`/`TaskUpdate`/…) renders as nothing because `TaskPanel` draws it, but an invisible item still *splits* a run in two — they are dropped inside `groupChatItems` instead, except when one is awaiting approval. (2) **⌘F walks the DOM and a collapsed group has none**, so `FindBar`'s `onOpen` now bumps an `unfold` counter through `ChatRowView` for the same reason it already drops the paging window; without it find silently searches half a conversation. Layout note: the chip's title and its mono detail must not shrink in proportion to their widths — a long `npx eslint …` beside "Lint the new files" turns the title into "Lint the ne…" while the command keeps three quarters of the row. The title is `flex: 0 0 auto`, capped at 50% only when something shares the row (`.chat-tool-name--capped`), so a dispatch with no detail beside it gets the full width.

## 2026-08-25 — The chat thread's cost was never DOM size — it was re-parsing finished markdown on every token, and…

2026-08-25: **The chat thread's cost was never DOM size — it was re-parsing finished markdown on every token, and `React.memo` on `ChatItemView` is the whole fix.** Measured over CDP on a real 216-row conversation (69 markdown blocks, 14,888 characters): a re-render with **every item unchanged** took a **35.1ms median**, against a 16.7ms frame budget — so a streaming turn could not keep up, and the work was `ReactMarkdown` re-running remark over messages that finished minutes ago. With `ChatItemView` and `ToolChip` memoized the same measurement is **4.0ms**, and 4.6ms with every group and chip force-opened (4,652 nodes). What makes memo *correct* here is a property of the reducer, not of the components: `replaceAt` and `patchTool` copy the items array and leave untouched elements alone, so item identity genuinely means "this message did not change" — and the other two props are stable by construction (`home` is a constant string, `onDecide` a `useCallback` on the pane id). Break that invariant in `reduceChat` and the thread silently stops updating. Three things worth knowing before optimising this again. (1) **Node count is a red herring**: paging already holds a fresh pane at ~580 nodes, and the earlier "a group opens 40 chips at once" worry measured as nothing — chips are cheap, parsing is not. (2) **A "load 50 earlier" press is not a re-render benchmark** — those items have never rendered, so memo cannot help them and the number stays ~130ms either way; the honest trigger is ⌘F, which bumps `unfold` and re-renders the thread with every item identical. (3) **`PerformanceObserver` on `longtask` has a 50ms floor**, so after the fix it reports nothing at all and reads like a broken probe; time from the dispatched event to the next macrotask instead. Separately, `chat-tool-output` now folds past `OUTPUT_PREVIEW_LINES` (120) behind a "Show N more lines" button, like `DiffView`: the box is 320px and scrolls, so about eighteen lines are ever visible, but the browser lays out every line it is handed and a `Read` of a large file hands it thousands. **Virtualisation was considered and rejected** — ⌘F walks the DOM (`FindBar` paints ranges over text nodes), so windowing the thread would make find search whatever happens to be mounted, and paging plus memo already put the cost two orders of magnitude under the frame budget.

## 2026-08-25 — Dictation is in the chat composer, and the only new idea it needed was an address. The mic, the Deepgram…

2026-08-25: **Dictation is in the chat composer, and the only new idea it needed was an address.** The mic, the Deepgram stream and the recovery file are all the notes pipeline unchanged (SPEC-NOTES §6); what was missing is that **one window runs every surface off one `stt:event` channel**, so an untagged event is one the renderer has to guess the owner of — and it guessed notes, which is where a chat dictation's words would have landed. `SttOwner` moved to `shared/notes.ts` and gained `'chat'`, `emit` in `main/stt.ts` stamps every event with the owner that started the capture, and `stt:start` takes one. Ownership is then checked **twice**, and both checks are load-bearing: main refuses a second capture outright (one mic, one owner), and `useDictation`'s `mine` ref drops events for a capture this pane did not start — panes are hidden with `display: none` rather than unmounted, so every mounted composer is listening. Three smaller rules. (1) The typed message survives: dictated words are appended to what was already in the box (`joinDictated`, pure and tested), and while the mic is open the box shows a preview while `value` still holds only the typing — so a dropped stream costs nothing. (2) **Escape belongs to the mic while it is open**, stopped from reaching the window listener that would otherwise interrupt the agent. (3) Send is disabled mid-dictation, because the words still arriving are not in `value` yet. The shortcut is **⌘P, and it matches `metaKey` only** — every other binding in the app takes `metaKey || ctrlKey`, but Ctrl+P is readline's "previous command" and these panes sit beside real shells, so accepting it would take a key back from every terminal (same reasoning that put the explorer on ⌘⇧B rather than ⌘B). **Auto-repeat has to be dropped** (`e.repeat`) or holding the keys down toggles the mic on and off many times a second — a toggle bound to a keydown is only the *first* keydown. It is registered in the composer and gated on `active`, like the pane's Escape-to-interrupt: every composer stays mounted, so an ungated listener would open the mic from whichever pane happened to register last — verified by listener count, which does not move when a second pane opens.

## 2026-09-18 — Files drop onto the whole chat pane, and an image is copied rather than referenced where it lies. Two kinds,…

2026-09-18: **Files drop onto the whole chat pane, and an image is copied rather than referenced where it lies.** Two kinds, split by what the runtimes can carry: the four types `stageImage` writes (png/jpeg/gif/webp) become chips through the same `stageAttachment` road a pasted screenshot takes, and everything else — a PDF, a folder, a HEIC, a source file — is *named* in the message for the agent to read with its own Read tool, since no runtime accepts a PDF as anything but a path. Copying a dropped image is not laziness about paths: `imageBlocks` only ever reads files sitting directly in `~/.chewo/attachments`, and that guard is the one thing stopping a renderer-supplied path from naming any file on the disk, so widening it to accept "wherever the user dragged from" would trade the guard for a byte copy of a screenshot. Five things learned building it. (1) **Electron removed `File.path` in 32** (this is 43), so the only way to learn where a dropped file came from is `webUtils.getPathForFile`, which exists in the *preload* and not in the renderer's world — `pathForFile` on the `api` bridge. It returns `''` for a drag that never came off the disk. (2) **The default action for a file dropped on a window is to navigate to it**, and on this frameless window that page sits on top of everything until ⌘R — the same hole the 2026-08-13 markdown-link entry describes. `main.tsx` swallows `dragover`/`drop` at the window for drags carrying `Files`, so nothing ever tries; main's `will-navigate` whitelist is the backstop, not the fix. Only file drags, or an internal card/tab drag would lose its own handlers. (3) The overlay must be `pointer-events: none` **and** the pane must count `dragenter`/`dragleave` rather than trusting a bare `dragleave`, which fires on every crossing into a child and flickers the overlay off over each message in the thread. (4) The composer owns the draft, so the pane hands files *down* through a `ComposerHandle` (`useImperativeHandle`, read through a ref so the function sees the current draft rather than the one it was created with) — lifting the draft up to the pane to avoid that would have moved every keystroke a component higher. (5) An inert composer (exited, or a parked permission request) shows **no** overlay at all rather than promising an attachment it would then drop: it already says why it is inert in its own placeholder. Verified over CDP — `Input.dispatchDragEvent` takes real `data.files` paths, so the whole path including `getPathForFile` and the staging IPC is drivable from a script. `dropPaths.ts` is pure and tested: relative to the checkout when the file is inside it, absolute otherwise, and a path with a space is backticked. There is deliberately no `@` prefix — that character is the picker's trigger, and an absolute path wearing it means something different to each CLI.
