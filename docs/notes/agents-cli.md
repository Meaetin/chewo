## 2026-08-25 — Codex interactive sessions now use the shared `ChatPane` through `codex app-server`; older entries saying a…

2026-08-25: **Codex interactive sessions now use the shared `ChatPane` through `codex app-server`; older entries saying a Codex selection swaps the pending pane to a pty are superseded.** Provider divergence stays in main (`codex-chat.ts` normalizes JSON-RPC into `AgentChatEvent`), while account usage is provider-selected (`account/rateLimits/read` for Codex, the existing OAuth reader for Claude). ## 2026-07-29 — There is no Claude SDK in this repo — no `@anthropic-ai/*` dependency exists. Every AI feature shells out to…

2026-07-29: **There is no Claude SDK in this repo** — no `@anthropic-ai/*` dependency exists. Every AI feature shells out to a CLI through `/bin/zsh -ilc`. The three headless ones (notes structuring, notes Q&A, todo voice) are **agent-agnostic**: pick the CLI per feature in Settings → Agents, stored in `userData/settings.json` under `agents`, read in main via `agentFor(task)`. **Add per-agent divergence only in `src/main/agent-runner.ts`** (`runAgentText` / `runAgentJson` / `chatCommand` / `normalizeChatEvent`) and describe the agent in `src/shared/agents.ts` — feature code must never branch on the agent. Gotchas that already bit: Codex's `--output-schema` is **OpenAI strict mode** (every property in `required`, `additionalProperties: false` — `toStrictSchema()` handles it) while Claude's `--json-schema` is looser; Codex emits whole `item.completed` messages, **not token deltas**, so `chat_text` carries a `delta` flag; Codex needs `--skip-git-repo-check` because the notes root and `~/.chewo` aren't repos. Never forward a CLI's raw event schema to the renderer — normalize to `ChatEvent` in main first. **Model lists are never hardcoded**: Claude uses its `--model` *aliases* (`opus`/`sonnet`/`haiku`/`fable`), which always resolve to the latest model of a tier; Codex is enumerated at runtime from `codex debug models` (`src/main/agent-models.ts`) because its catalog is server-driven and genuinely changes between calls. Reasoning effort is **per model, not per agent** — read it off the selected model, never a global list.

## 2026-07-29 — Interactive spawns are agent-agnostic too — anything that launches a session (card runs, worktrees,…

2026-07-29: **Interactive spawns are agent-agnostic too** — anything that launches a session (card runs, worktrees, new-session) must offer both CLIs, never hardcode `source: 'claude'`. Both take the prompt as a **positional argv** and auto-submit it (`claude [flags] '<prompt>'` / `codex [flags] '<prompt>'`); the divergence lives in `promptFlags()` in `src/main/terminals.ts` and is images only. Claude reads image *paths* found in the prompt, so it just needs the assets folder unlocked with `--add-dir`; **Codex has no read-side `--add-dir`** (its flag grants *write* roots) and its file tools can't read a PNG, so files are attached with `-i <file>` per image. Both flags are **variadic**, so the prompt always goes first and flags last — reversed, the CLI parses the prompt as another value and starts with no prompt at all.

## 2026-07-29 — Our MCP server is named `chewo` (`packages/chewo-mcp`, package `@chewo/mcp`, tools reach models as…

2026-07-29: **Our MCP server is named `chewo`** (`packages/chewo-mcp`, package `@chewo/mcp`, tools reach models as `mcp__chewo__*`); the old `context-bridge` name survives only as `LEGACY_MCP_SERVER_NAME` for migration. It **ships inside the app** as an extraResource (`Resources/bin/chewo-mcp.cjs`) — never assume the user installs or registers it separately, and never register it with `node <path>`: Claude Code is a native binary and Codex is Rust, so a user can have both CLIs and no Node. The command is always **Chewo's own binary with `ELECTRON_RUN_AS_NODE=1`**. Registration is **opt-in in Settings → Connections**; `reconcileMcpServer()` at launch only repairs a registration the user already made (packaged builds only — in dev it would fight the installed app over the same config entries). Reads parse `~/.claude.json` / `~/.codex/config.toml` directly, **writes always shell out to `claude mcp add|remove` / `codex mcp add|remove`** (same doctrine as `mcp-writer.ts`). Server state is `~/.chewo/mcp/` (inbox + audit.log). Renderer-safe names/types live in `src/shared/chewo-mcp.ts`, fs paths in `src/shared/mcp-paths.ts` — keep node imports out of the former.

## 2026-08-03 — Interactive sessions open on the best model at high effort, and neither default names a dated id.…

2026-08-03: **Interactive sessions open on the best model at high effort, and neither default names a dated id.** `NEW_SESSION_DEFAULTS` in `shared/agents.ts` is Claude → `opus`, Codex → the **head of its own discovered catalog** (`codex debug models` is priority-ordered, so entry 0 is the CLI's "latest frontier" slot — `gpt-5.6-sol` today), both at effort `high`. Deliberately *not* `AgentDef.defaultModel`, which stays "let the CLI decide" for the headless features. `sessionModel`/`sessionEffort` are the single resolver used by both the composer's picker and the spawn, so a session can never run on a model the row was not showing; effort is **clamped to the model's own `efforts`** because the set is per model (gpt-5.5 has no `max`, gpt-5.6-sol adds `ultra`) and an unaccepted level fails at spawn. `TerminalTab.model`/`effort` hold the user's override only — absent means "resolve", so a CLI update that renames a model doesn't strand a tab. Switching agent clears both (a model id belongs to one catalog). The flags diverge in `modelFlags` (`src/main/terminals.ts`): claude takes `--model`/`--effort`, **codex has no effort flag** and takes `-c model_reasoning_effort="…"`. Both values are `shellQuote`d rather than validated against an enum the way `permissionFlag` is — the accepted set is discovered at runtime, so quoting is the only guard that a catalog string reaches the command line as exactly one argument.

## 2026-08-17 — Codex has subagents now — SPEC-CAPABILITIES.md §1/§2 and the `AgentRef` comment ("CC only") are stale.…

2026-08-17: **Codex has subagents now — SPEC-CAPABILITIES.md §1/§2 and the `AgentRef` comment ("CC only") are stale.** Verified on this machine: `codex features list` reports `multi_agent` as **stable, enabled** (codex-cli 0.144.5), and the binary carries `developer_instructions` (required, and it rejects a blank one), `agents.max_depth`, `agents.max_threads`, `agents.job_max_runtime_seconds`, and a `features.multi_agent_v2.*` block (`max_concurrent_threads_per_session`, the wait timeouts, `subagent_usage_hint_text`, `hide_spawn_agent_metadata`). Its own warning string says subagents "can increase usage quickly. Consider setting … below 8." Per the docs, definitions are **TOML** in `~/.codex/agents/` and `<proj>/.codex/agents/` — `name`, `description`, `developer_instructions`, plus any `config.toml` key (`model`, `model_reasoning_effort`, `sandbox_mode`, `mcp_servers`); neither directory exists here yet, so **verify the loader path against the installed binary before writing to it**. Claude's half is `<proj>/.claude/agents/*.md` and `~/.claude/agents/*.md`, markdown with YAML frontmatter, and the body is the *entire* system prompt — a subagent does not inherit Claude Code's own. Three consequences. (1) **These are not portable the way `SKILL.md` is.** That cross-agent standard is why skills copy unmodified; agent definitions are two formats with different semantics, and the tool policy especially does not map (Claude names tools in `tools`/`disallowedTools`, Codex sets `sandbox_mode`), so "install to both" is a lossy translation and must be labelled as one. (2) The **`description` field is the router** — it is what the main agent reads to decide whether to delegate, so it is load-bearing prose, not a caption. (3) **Doc/build drift is real**: the docs name `agents.default_subagent_model` and that string is absent from the 0.144.5 binary — treat the published field list as a hypothesis and pin it with a canary the way `npm run canary:chat` pins the wire format. Related auth note, latent rather than broken: `buildPtyEnv` scrubs `CLAUDECODE`/`CLAUDE_*` but not `ANTHROPIC_API_KEY`, and every pane spawns through `/bin/zsh -ilc` — an exported key in the user's shell rc would silently move the whole app, subagents included, off the subscription and onto pay-per-token billing. Not set on this machine; worth detecting and warning about rather than scrubbing, since some users mean it.

## 2026-08-17 — The agent builder is one CLI call and four pure modules, and the split is forced by what can import electron.…

2026-08-17: **The agent builder is one CLI call and four pure modules, and the split is forced by what can import electron.** `main/agent-builder.ts` holds only the spawn — timeout, neutral cwd, model pin — because it reaches Settings through `agentFor('agentBuild')` and `settings.ts` imports `electron`, which puts anything in that file out of reach of both the renderer and a canary (`tsx` dies with "does not provide an export named 'app'"). Everything else is shared and pure: `capabilities/agent-file.ts` is the on-disk format (serialize/parse/sanitize), `capabilities/agent-draft.ts` is the builder's request, JSON Schema, prompt and the reconciliation of what comes back, and `capabilities/frontmatter.ts` is the parser **extracted out of `scan.ts` for exactly this reason** — `scan.ts` reads directories and so imports `node:fs`, so the agent editor previewing a file would have pulled the filesystem into the renderer bundle (same trap `shared/chewo-mcp.ts` documents). Five things measured or decided here. (1) **Latency is 41–72s** at opus/high for a 4–6 KB system prompt (`npm run canary:agent`, CLI 2.1.233, two runs) — so `gitText`'s 90s would kill a working call about half the time, and `TIMEOUT_MS` is 180s. Erring long is free because there is **no fallback**: unlike a commit message, where a deterministic local string beats a slow model, a locally-invented system prompt would be worse than an honest failure, so a failure is reported rather than papered over. For the same reason the blank-model pin is the *opposite* of `gitText`'s — `CAPABLE` is opus/high, not opus/medium, since this runs once per agent and quality dominates. (2) **`preload` is forced off whatever the model says.** The `skills:` frontmatter preloads a skill's full body at startup on every invocation (~50,000 tokens for figma's 12 against ~500 for their descriptions), so it is the user's call on the review screen; the drafting model only proposes *which* skills, each with a `reason` that is shown and **never written to disk**. (3) A skill name the model invented is **dropped**, not carried — an unknown name in `skills:` is a preload that fails at spawn, and nothing in the UI can distinguish a hallucinated skill from an uninstalled one. (4) **Overwriting is the edit path**: `writeAgent` reads the existing file and hands it to `serializeAgent`, which carries every unmodelled frontmatter key (`permissionMode`, `maxTurns`, `hooks`, whatever a CLI update adds) through in its original position — the failure mode without it is silent, since the agent still loads. That is also why the frontmatter is rewritten line-by-line rather than through a YAML round-trip, which would renormalise quoting and ordering across lines the user never touched. (5) `tools: []` and an omitted `tools:` are **opposites** — omitted grants every tool, `[]` grants none — so an empty allowlist must never be emitted, and `toolPolicy` in `CapabilityRows.tsx` must never render one as a restriction.

## 2026-08-17 — Three bugs in the agent builder's review screen were invisible to typecheck, 596 tests and a clean build, and…

2026-08-17: **Three bugs in the agent builder's review screen were invisible to typecheck, 596 tests and a clean build, and all three fell out of driving the app.** (1) `capabilities:readMemory` **refuses anything that is not CLAUDE.md/AGENTS.md**, so the Edit button failed on every agent with "refusing to read non-instruction file". The fix is `readAgentFile`, a second narrow door (a `.md` whose parent directory is literally `agents`) — *not* a widened whitelist, because that guard is the only thing stopping an IPC channel named "read a file" from becoming one. (2) The preview pane rendered `serializeAgent(draft)` with no second argument, so it showed a file **missing every unmodelled frontmatter key** — `permissionMode`, `maxTurns`, `hooks` — while the actual save preserved them, directly under a subtitle reading "Nothing it does not show is lost". The modal now takes the file's original text as `edit.source`; a preview that disagrees with the write is worse than no preview. (3) A disabled plugin's skills were labelled **"not installed"**, which is simply false — they are on disk and reach nobody. `SkillOption.unavailableReason` carries the true words ("the figma plugin is disabled") and the row and the warning both use it. Two layout notes from the same pass: `ModalShell` grew an `xwide` (880px) step because `wide` is 640px and a subagent's system prompt wraps to about seventy monospace columns there, and any flex row nested inside a modal field needs `width: 100%` or it sizes to max-content and overflows — same trap as `.capability-row__line`. The GUI was driven over CDP with the `ws` already in `node_modules` (`npx electron out/main/index.js --remote-debugging-port=9787`); **ports 9222 and 9333 are squatted on this machine** by an unrelated Chrome. Screenshot the result and look at it — bug (2) was legible only as two missing lines in a `<pre>`.

## 2026-08-17 — Installing an expert agent does not make it get used — delegation is a judgement, not a routing table, and it…

2026-08-17: **Installing an expert agent does not make it get used — delegation is a judgement, not a routing table, and it loses to "I can just do this".** Verified live: a session with `figma-expert` installed *and* the Figma MCP tools available called those tools itself and never delegated, and `claude -p` confirms the agent was loaded and offered the whole time. The `description` is only a suggestion the main model reads; a subagent wins that judgement when it offers something the main agent lacks (a clean context, a narrower tool policy), and when the main session already holds the same tools it offers nothing. So Chewo has a **Lead toggle** on the composer's setup row: `orchestratorBrief` (pure, `shared/orchestrator.ts`) is passed with `--append-system-prompt` alongside `--forward-subagent-text`, and the roster is resolved at spawn by `main/roster.ts`. Six things hold it together. (1) **It is opt-in and must stay so** — delegation costs a fresh context that cannot see the conversation, which is the wrong trade for the small edit most sessions are; the brief therefore carries a "when not to delegate" half, without which a one-line CSS fix becomes a three-agent fan-out. (2) It is **spawn-time**, like the checkout picker, so it is offered only while the pane is `pending` — `--append-system-prompt` cannot be added to a live session. (3) An empty roster returns `''` and the flag is not passed at all: briefing a lead to dispatch to nobody produces an agent that announces a plan and then does everything itself, which reads as the feature being broken. (4) Agents in **disabled** plugins are excluded — the CLI will not launch them, and naming an agent that cannot start is worse than omitting it. (5) `listInstalledPlugins` is now cached 30s and single-flighted because it is a process spawn and sits on every project selection; **agent files are deliberately not cached**, since writing one and using it in the next session is the point. (6) Attribution comes from `launchedAgent` (`shared/subagent.ts`), which reads `subagent_type` off the `Agent`/`Task` call — matched by exact name, never by prefix, because `TaskCreate`/`TaskUpdate`/`TaskList`/`TaskGet`/`TaskOutput`/`TaskStop` all start with `Task` and launch nothing. Identity is two initials plus a hue (`shared/agent-identity.ts`): FNV-1a rather than a character sum, because a sum gives near-identical names neighbouring hues and those are exactly the ones needing to be told apart. Note the CLI's built-in agents (`Explore`, `Plan`, `general-purpose`) are not files and so never appear in a scan-derived roster — the count in the toggle is *your* agents, which is the honest number.

## 2026-08-25 — Model and effort are live for the whole session — freezing them after the first message was Chewo's limit,…

2026-08-25: **Model and effort are live for the whole session — freezing them after the first message was Chewo's limit, not either CLI's.** The composer's setup row used to vanish once a pane started (`setup={started ? undefined : setup}`), so a resumed session offered nothing but a text box. It now stays, minus the two questions that really are settled: the agent (a different CLI is a different conversation) and the checkout. Verified live, not read: **Claude takes a `set_model` control request** (`{subtype:'set_model', model}` — acked, and the CLI then re-emits `system/init` carrying the new model, which `ChatPane` already consumes, so the readout updates itself), and has **no control request for effort** — only `/effort <level>`, which it handles locally, answering with one confirmation line and never reaching a model. **Codex takes both on `turn/start`**, whose generated schema calls each an override "for this turn and subsequent turns" (`codex app-server generate-json-schema --out <dir>` prints the whole protocol; `TurnStartParams` is the file to read). So `setChatModel`/`setChatEffort` in `chat-sessions.ts` are one function each with a per-CLI branch, and Codex's half is just a field on the record that rides the next turn. Two things that are choices. (1) **The pickers rest while a turn is in flight** — Claude's `/effort` would queue behind the work, and Codex would apply the override to the turn already being spoken. (2) **Lead is shown disabled with the reason, not hidden**: the brief goes in with `--append-system-prompt` (Claude) / `developerInstructions` at thread start (Codex) and neither has an update path, so it is the one thing on the row that genuinely cannot change. Related find while probing: **the `initialize` reply also carries a full model catalog** — `value`, `resolvedModel`, `displayName`, `description`, `supportedEffortLevels` per model — which would replace the hardcoded Claude aliases in `shared/agents.ts` and give the alias↔id mapping for free. Not taken yet; `matchModelId` does it by longest-alias substring instead.

## 2026-08-25 — A resumed pane can read its own model and effort off the transcript, and it has to, because neither CLI will…

2026-08-25: **A resumed pane can read its own model and effort off the transcript, and it has to, because neither CLI will say.** `--resume` replays nothing and spawns with no `--model`/`--effort` flag, so a resumed session's first announcement of what it is running is `system/init` — one whole turn *after* the point where you would want to change it. Both formats record it per turn: **Claude puts `model` on `message` and `effort` as a sibling of it, on every assistant record** (verified across real 2.1.240 sessions: 213/213, 14/14, 16/16), and **Codex writes a `turn_context` before each turn carrying `model` and `effort`**. `ParseResult` now carries both, read by the same backwards walk `contextTokens` uses — newest first, main-branch only, because a Claude sidechain record is a *subagent* on another model and reporting it would put a model the user never chose in front of them, and `session_meta` is the wrong Codex record for the same reason in time rather than in branch (a thread can be moved onto another model mid-conversation). `ChatPane` orders three sources: what the user picked, what this session's own `system/init` said, then the transcript. Found on the way: **`seedItems` was printing `//effort low`** — Claude writes `<command-name>/effort</command-name>`, slash included, and the renderer added another; the slash is normalised now rather than prefixed, which had been wrong for every slash command in every resumed transcript.
