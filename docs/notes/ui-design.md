## 2026-07-19 — For draggable UI (code tabs, cards), use native HTML5 DnD (`draggable` +…

2026-07-19: For draggable UI (code tabs, cards), use native HTML5 DnD (`draggable` + `onDragStart`/`onDragOver`/`onDrop`/`onDragEnd`), matching `TodoBoard.tsx`. Critical gotcha: **never put `user-select: none` on the draggable element** — on this macOS Chromium/Electron it silently suppresses native drag initiation (element goes inert: no drag, no text selection). Native drag cancels text selection on its own, so it isn't needed. Dead ends that were tried and reverted: native DnD *with* `user-select: none` (cursor changes, nothing drags) and a pointer-events/`setPointerCapture` rewrite (highlights tab text instead of dragging).

## 2026-07-21 — Second way to kill native drag in the same component: never mount, unmount, or resize an element in the drag…

2026-07-21: Second way to kill native drag in the same component: **never mount, unmount, or resize an element in the drag source's layout flow from `onDragStart`**. The T5 run strip rendered as `{draggingId && <strip/>}` above the columns — the state change reflowed the grid under the card mid-`dragstart` and the drag silently never began (symptom identical to the `user-select` bug: card feels inert). If such an affordance is ever needed again, keep it **always mounted and absolutely positioned**, toggling only `opacity`/`pointer-events`, which don't reflow — that fix worked, though the strip itself was then dropped for a modal button. Toggling a class on the dragged card itself (e.g. `.todo-card-dragging { opacity }`) is fine.

## 2026-08-03 — A popover pinned below its trigger is invisible in the composer — `Select` flips above when the room is up…

2026-08-03: **A popover pinned below its trigger is invisible in the composer — `Select` flips above when the room is up there.** The setup row (agent/model/effort) lives at the bottom of the window permanently, so `top: rect.bottom + 4` with `maxHeight: innerHeight - rect.bottom - 16` gave every one of its menus a few pixels or a negative height: the dropdowns opened and showed nothing. The rule is now `placeMenu` in `src/renderer/src/selectPlacement.ts` — DOM-free and tested (`tests/select-placement.test.ts`), like `selectFilter.ts` next to it — and it flips whenever below is short *and* above is roomier, anchoring by `bottom` so the menu grows away from the trigger rather than over it. **Do not make it unconditionally drop up**: the same bug mirrors for a settings row near the top of a modal. It also clamps `left` against the right edge, which `menuMinWidth` (260 on a trigger ~60px wide) can otherwise overhang. **There is no prettier in this repo** — no config, no dependency, no `format` script — so `npx prettier --write` fetches one with *default* settings and rewrites the whole file with semicolons and double quotes. Match the surrounding style by hand; `npm run typecheck` and `npm test` are the only formatting-adjacent gates.

## 2026-08-03 — The tab bar belongs to the tabs — everything else in it had to justify its width, and most of it couldn't. At…

2026-08-03: **The tab bar belongs to the tabs — everything else in it had to justify its width, and most of it couldn't.** At four sessions the right-hand cluster was ~430px of pinned controls against a strip whose tabs were `flex: 0 0 auto`, so they never shrank; they scrolled off the left edge with no fade, no arrow and no menu, and the clipped tab was indistinguishable from no tab. Four things changed and each has a rule behind it. (1) **The branch chip is deleted.** A worktree tab's label *is* its task name and its branch is `agent/<that slug>`, so the widest control on the rail restated the tab beside it — and its dashed pending variant restated the composer's own "Its own branch, from origin/main" row, on screen at the same time. Its detail moved to the tab's `title` (`tabTitle` in App) and the git panel header, which is per-tab rather than focused-only, and free. (2) **Update renders only when `behind > 0`** — which first required making `behind` mean something: git emits `# branch.ab` **only for a branch with an upstream**, and every session's branch is cut `--no-track`, so `behind` read 0 forever on exactly the checkouts whose base moves under them. `gitStatus` now counts `HEAD..origin/<default>` itself when there is no upstream and reports what it measured against as `RepoStatus.baseRef`; `defaultRemoteRef` moved from `git-ops.ts` to `git.ts` for it (a pure read, and importing the mutation file from the read-only one would have been a cycle) and is re-exported from its old home. Verify this claim before trusting any ahead/behind in this app: `git status --porcelain=v2 --branch` in a session worktree prints no `branch.upstream` line at all. (3) **▷ moved to the sidebar's project row**, where its scope is visible — it runs dev servers in the project's *main* checkout, so it never belonged to the focused session's bar; it takes a `projectId` now and selects that section, because `openTerminal` sets the view but not the section, and a shell opened for an unselected project would show a pane with no tab. `+` stayed: a plus at the end of a tab strip is a universal idiom. (4) **Tabs shrink to a 132px floor, then scroll**, with edge fades and a ⌄ menu of every session (`TabOverflowButton`), shown only while something is genuinely off-screen. Three traps in that last part. The fades are **pseudo-elements on a wrapper**, not a `mask-image` on the scrollport — a mask clips to the element box and would shear off the active tab's -1px bleed into the terminal, the same bleed the strip's `padding-bottom: 1px` / `margin-bottom: -1px` pair exists to protect. The hidden-tab count is measured with `getBoundingClientRect`, **not `offsetLeft`**, whose offsetParent is a positioned ancestor of the scrollport and so is not in the same space as `scrollLeft`. And focusing a session always scrolls its tab back into view, or the focused pane has no tab — the exact state the menu exists to rescue, reached by accident. The overflow arithmetic is `src/renderer/src/tabStrip.ts`, DOM-free and tested like `selectPlacement.ts`.

## 2026-08-09 — A typo'd design token is not a fallback, it is a dropped declaration — `--space-10` does not exist. The scale…

2026-08-09: **A typo'd design token is not a fallback, it is a dropped declaration — `--space-10` does not exist.** The scale is 2/4/6/8/12/16/20/24/32 (styles.css line ~91, several per line, which is why a careless grep for the definition finds nothing and a careless grep for *uses* looks fine). An unresolvable `var()` makes the whole property invalid *at computed-value time*, so `padding: var(--space-8) var(--space-10)` does not fall back to the 8 — it falls back to the initial value, **0**. That is what jammed the Ship modal's route chips ("Open a pull request" / "Push straight on") against their own borders; the two `margin-bottom: var(--space-10)` beside it had simply never applied, and the section's `gap: var(--space-6)` had been doing all the spacing for months. Two things worth keeping: the audit is `grep -o -- "var(--[a-z0-9-]*)"` minus `grep -o -- "--[a-z0-9-]*[[:space:]]*:"`, both sorted and `comm`'d, which finds every phantom token in one pass (it now reports only `--border-subtle`, used once at line ~5232 and also undefined); and **pair every `font-size` token with its `--lh-*` twin** the way the rest of the file does — the chips had neither, so their height was whatever the inherited line-height happened to be. There is no stylelint and no prettier here, so nothing but that grep will ever tell you.

## 2026-08-24 — A light theme is a direction flip in three derived ramps, not a second stylesheet — and the CSS block that…

2026-08-24: **A light theme is a direction flip in three derived ramps, not a second stylesheet — and the CSS block that finishes the job can only hold tokens JS never writes.** `isLightBase` (base lightness > 55) is the single switch, exported from `shared/appearance.ts` so the surface math, `applyAppearance`, `makeEditorTheme` and the preset gallery never disagree about which way round the app is. Four things it turns. (1) `deriveSurfaces` subtracts its offsets instead of adding them, so a raised surface *darkens* — the GitHub-light shape, white window and grey hover, which also keeps hover/press reading as "more emphasis". (2) `deriveTextRamp` swaps its cream anchors for ink ones (`#202326 / #474d55 / #6a737f / #959da6`), picked to match the cream ramp's own contrast on graphite level for level rather than to match anybody's hex. (3) `deriveRim` goes to alpha 0.7 — a white hairline at 0.05 is invisible on a light card. (4) **A light ramp holds *chroma* steady rather than HSL saturation**: HSL compresses saturation near white, so Solarized's `#fdf6e3` measures s=87% while its own next surface `#eee8d5` is s=42%, and carrying s down the ramp turns a cream into custard. Dark ramps deliberately keep s flat — the shipped dark presets were authored against that and Nord's real ramp does the same, so this correction is light-mode only. Two traps around the CSS. **`applyAppearance` writes inline styles on `documentElement`, which outrank `:root[data-theme='light']`** — so that block may only hold tokens the function never sets (shadows, scrim, danger/warning, badges, diff, and the accent hover/press/text steps, which have to run *down* on a light surface); putting `--c-live` or `--c-project` there does nothing, because both are written inline from the preset's own accents. And **`--c-on-accent` cannot be a fixed dark ink**: `inkOn()` scores the accent's own near-black and near-white twins by contrast and picks the winner, which is what stops a deep accent (a light theme's saturated blue) from rendering its button label at 2:1. Preset note: **GitHub Light survives the 3:1 bar untouched; Catppuccin Latte and Solarized Light do not** — several of their own colours sit under it on their own paper, and both were built, screenshotted and then dropped rather than shipped darkened under their names. `tests/appearance.test.ts` pins the flip, the chroma rule and the per-slot contrast; the ANSI bar deliberately skips `black`/`brightBlack`/`white`/`brightWhite`, since the ends of that ramp are low contrast by definition (the stock graphite preset's own `black` sits at 1.1:1).

## 2026-08-24 — The three accents are three signals, not a colour harmony — and picking them out of one palette family is…

2026-08-24: **The three accents are three signals, not a colour harmony — and picking them out of one palette family is what broke them.** `accent` means you-are-here, `accentSecondary` paints the expanded project's wash and left bar (this-container-is-open), `accentTertiary` paints every live dot, running row and in-flight tool chip (an-agent-is-working). Measured across the shipped presets, **five of seven put the live colour within 30° of the accent — the default among them** (emerald h156 against a cyan h185), so a running session read as a slightly bluer focused one; Nocturne was three shades of one colour (17°/14°/31°) and its secondary only cleared 4.4:1. Two rules now hold, both pinned in `tests/appearance.test.ts` so a new preset cannot quietly reintroduce it. (1) **All three at least 45° apart in hue**, which is why the default's live is now magenta `#ef7fc8` rather than the cyan it was. (2) **Clear of the hues the fixed status colours already own** — danger/diff-del (h5), the Claude badge (h17), warning (h38), diff-add (h135), the Codex badge (h214) — since landing on one makes two different things the same colour. Those exclusions leave exactly three usable bands, **64–109, 161–188 and 240–339**, which is a tighter budget than it looks: an emerald accent at h156 rules out the middle band entirely, so its live colour *cannot* be the conventional cyan and stays pink. The emergent convention is secondary = the theme's cool violet/teal, tertiary = a vivid magenta-pink — except where the accent already owns pink (Nightshade, Rosé), where live takes the turquoise slot instead. Nocturne is the other exception: Nord's aurora set has only purple and green far enough from its frost accent, so live is `#a3be8c`. **There is no migration**: `loadSettings` deep-merges over `DEFAULT_APPEARANCE`, so anyone whose `settings.json` already holds an explicit `accentTertiary` keeps it, and the fix only reaches them when they pick a preset or edit the two colours in Settings → App. That is deliberate — silently rewriting a colour somebody chose is worse than leaving it.

## 2026-08-24 — Setting a font is two edits; making it actually reach the whole app is four. The UI stack is Plus Jakarta…

2026-08-24: **Setting a font is two edits; making it actually reach the whole app is four.** The UI stack is Plus Jakarta Sans at weight 400, self-hosted from `src/renderer/src/assets/` (`fonts.css` + four woff2), imported at the top of `styles.css` and linked from `hud.html` — the voice HUD is a separate entry with its own inline `<style>` and no stylesheet import, so a font change that only touches `styles.css` silently misses it. Vite hashes the woff2 into `out/renderer/assets/` for both entries off one copy; verify with `grep -o "url([^)]*)" out/renderer/assets/*.css` after any change, since a broken path fails to a fallback face rather than to an error. Three traps. (1) **`body` had a hardcoded `-apple-system` stack**, not `var(--font-ui)` — the token existed and the body ignored it, so the stack was set in two places and only one of them was the one that mattered. (2) **Form controls do not inherit `font-weight`.** The UA sets it on `button`/`input`/`textarea`/`select` by element selector, and the repo hands them `font-family: inherit` one rule at a time without ever handing them the weight — so any resting weight other than 400 stops at their border and they read a shade off the text beside them. One reset near the top of `styles.css` fixes it; do **not** reach for `* { font-weight }`, which beats the UA's `strong`/`b`/`h1` rules and kills every bold in the app. (3) **Light 300 was tried and reversed the same day.** Every heading above 15px here is serif (`--font-display`), so the sans face only ever renders at 11–15px and there is no display size for a display weight to live at; and the change is width-neutral — measured in-app, one sidebar title is 163px in SF Pro 400, 164px in Plus Jakarta Sans 400 and 163px at 300 — so weight buys no density and costs only stem contrast, which small grey text on a white base cannot spare. The resting weight is `--weight-body`, deliberately *not* a redefinition of `--weight-regular`: one token moves the whole app and the ramp keeps meaning what it says. Checked on screen over CDP: `document.fonts.check('300 13px "Plus Jakarta Sans"')` is the honest probe, because a computed `font-family` naming the family proves only that the CSS parsed.

## 2026-09-18 — Every shortcut the app owns lives in `src/shared/keybinds.ts`, and the stored format is an Electron accelerator

Ten shortcuts were spread across seven files as hand-written `(e.metaKey || e.ctrlKey) && e.key === 'x'` checks, and thirteen button labels plus eight context-menu hints spelled their chord as a literal string — so a rebind was impossible and a label could not be wrong, only stale. `KEYBINDS` is now one registry (id, label, detail, group, scope, default); user overrides live in `settings.json` beside appearance and are merged over the defaults on load, so a file written before a shortcut existed picks it up.

**The stored format is Electron accelerator syntax**, not a shape of our own, because `globalShortcut` takes nothing else and the voice hotkey is a real system-wide registration — one value has to serve both that and the window listeners. `matchesKeybind` reads the same strings against DOM events, `toCodeMirrorKey` converts for the editor's keymap, `formatKeybind` renders ⌘⇧E for labels. Mac glyphs unconditionally: this is a macOS app, and a hint reading "Ctrl+Shift+E" on a machine whose keyboard says ⌘ is worse than wrong.

Four rules the matcher follows, each of them load-bearing. (1) **Modifiers match exactly**, or ⌘⇧P would fire dictation as well as the run command — the old handlers got this right by hand and the matcher has to keep it. (2) `CommandOrControl` is the only either-side modifier and only ever a *default*; a chord the user records is stored as the keys they pressed (`Command+Shift+K`), so rebinding dictation off ⌘P cannot quietly hand **Ctrl+P back to readline** — the whole reason ⌘P is meta-only. (3) **Shift is exact for letters, digits and named keys and ignored for punctuation**, because the punctuation often needs Shift to type at all: ⌘= and ⌘+ are one request, which is what the old terminal-zoom handler did by testing both characters. (4) Conflicts are checked per scope and `CommandOrControl` collides with both of its halves, so the recorder refuses a taken chord and names the command holding it.

Three wiring traps. (1) **The CodeMirror find panel is rendered into its own `createRoot`**, outside the React tree, so no provider reaches it — it reads a module-level mirror App keeps current (`keybindNow`). (2) Making the editor's Find bindable means turning off `basicSetup`'s `searchKeymap` and re-adding it minus its `Mod-f` entry, or ⌘F would keep working after a rebind and the settings pane would be lying; its companions (⌘G, ⌘⌥G, ⌘D) are not rebindable and are kept exactly as CodeMirror ships them. (3) The recorder swallows keys in the **capture** phase, which silences every bubble-phase shortcut but not a capture listener registered earlier — the chat find bar is one, so it checks `keybindRecording()`.

The voice hotkey moved out of `projects.json` (`todoHotkey`) into the keybinds map; `migrateTodoHotkey` adopts it at launch and deletes it from the old file, before the renderer can save either one. Verified over CDP on a real launch: the old value landed in settings.json and left projects.json. Also deliberate: the pane lists the **fixed** keys too (Escape, Enter, Tab, arrows, ⌘C/⌘X/⌘V, ⌘⌫), because a pane showing only what you can change answers half the question you opened it with. The line between the two is that a shortcut has a modifier and the app chose it; a bare key is interface behaviour, and the clipboard chords are OS conventions.

## 2026-09-19 — The recorder ignored a bare key in silence, and Option chords recorded the character Option types

Two defects in the Keybinds pane, both found by driving the app with **real** keystrokes (`osascript`, System Events) rather than CDP-injected ones. Injected keys bypass the OS and the application menu, so the first round of verification could not have caught either.

**A bare key was refused with no feedback**, which is what "pressing keys does nothing at all" turned out to mean. `accelFromEvent` returned `null` for both "a modifier on its own, keep waiting" and "a key with no modifier, refused" — one value for two very different situations, and the pane had nothing to say about either, so it sat on *Press keys…* forever. It is now `recordChord`, returning three things: `null` still means half a chord and stays quiet, `{ ok: false, reason }` carries a sentence the row prints, and `{ ok: true, accelerator }` applies. **Function keys are now accepted bare** (`F1`–`F20`), because the refusal only exists to stop a binding that would swallow typing and an F-key types nothing.

**macOS substitutes the character Option types into `event.key`**, so ⌥⌘K arrives as `˚` and was stored as `Command+Alt+˚` — a string `globalShortcut` cannot register (it would have broken the voice hotkey outright) and that renders as a meaningless glyph on the button. The fix reads `event.code` for the physical key, but **only when Option is down**: `code` is layout-independent, so consulting it unconditionally would make a Dvorak or AZERTY keyboard fire the wrong binding. It has to happen in *two* places or the feature is half-built — `recordChord` stores `Command+Alt+K`, and `matchesKeybind` adds the physical key to the candidate list, or the binding would record cleanly and then never fire. Accelerators already saved in the broken form still match, since the typed character stays in the candidate list too.

Two things worth knowing before driving this app with System Events again. (1) **`set frontmost` has to run before every keystroke**, not once at the top of a sweep — the app quietly loses focus between steps and the keys land somewhere else, which reads exactly like "the chord was swallowed by the menu" and cost two wrong diagnoses here. (2) Re-clicking a chord button that is already armed *disarms* it, so a test harness that clicks before each press silently tests nothing.

Not a bug, verified while here: ⌘A, ⌘C, ⌘Z and ⌘R all reach the renderer and are recordable — the `editMenu`/`reload` roles do not swallow them while the web contents hold focus, and the recorder's `preventDefault` stops ⌘R from reloading mid-recording.
