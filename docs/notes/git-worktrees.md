# Git, worktrees and Ship

Full notes moved out of `AGENTS.md` so they are read on demand, not loaded
into every session. Text is verbatim; the index lives in `AGENTS.md`.

## 2026-07-29 — Worktree truth comes from git, not from `projects.json`. The sidebar's "Isolated branches" group is…

2026-07-29: **Worktree truth comes from git, not from `projects.json`.** The sidebar's "Isolated branches" group is reconciled against `git worktree list --porcelain` (`listWorktrees` in `src/main/worktrees.ts`), because the records drift: dev and packaged builds keep **separate** `projects.json` files, and closing a pane deletes the `SavedTerminal` that was the branch's only handle. Two gotchas if you touch this. (1) **"0 commits ahead of main" cannot tell a fresh worktree from a merged one** — both sit at zero. Anything that decides a branch is done must compare the tip against the commit it was *cut at* (`Worktree.baseCommit`, recorded at creation, recovered from the branch reflog's `branch: Created from X` entry when adopting), and must treat unknown provenance as still-live: locking a fresh worktree is far worse than leaving a spent one open. Uncommitted changes always keep a branch live. A squash/rebase merge rewrites SHAs and is deliberately *not* detected — the merge modal's **Mark as done** sets `Worktree.doneAt`, the hand override for exactly that, undoable from the row. (2) The `Row` primitive (`components/ui/Row.tsx`) **paints its own live dot** from the `live` prop — passing a `<Dot tone="live"/>` as `leading` renders a second one.

## 2026-07-29 — `git status` collapses a wholly-untracked directory into one entry with a trailing slash (`? packages/foo/`),…

2026-07-29: **`git status` collapses a wholly-untracked directory into one entry with a trailing slash** (`? packages/foo/`), so a status entry is not always a file. Diffing one is a trap: `git diff --no-index -- /dev/null <dir>/` resolves `/dev/null`'s *basename* inside the directory and dies with `error: Could not access '<dir>/null'` — the panel's "Could not access …/null" bug. `ChangedFile.isDir` now flags these, `gitDiff` refuses them, and `GitPanel` expands the row via `gitUntrackedFiles()` (`git ls-files --others --exclude-standard`, capped at 500). **Do not "fix" this by switching status to `-uall`** — one unignored build dir turns 1 row into 517 (measured on this repo against a stale 318 MB Swift `.build/`, since deleted).

## 2026-07-30, narrowed 2026-08-03 — `src/main/git.ts` is read-only by contract; every git *mutation* lives elsewhere, split by blast radius —…

2026-07-30, **narrowed 2026-08-03**: **`src/main/git.ts` is read-only by contract; every git *mutation* lives elsewhere, split by blast radius** — `git-ops.ts` (bring commits in), `git-ship.ts` (send work out), `worktrees.ts` (checkout lifecycle). Keep that split so "does this touch the repo?" is answerable by filename. Same house rules everywhere: never `--force`, never `-D`, never stash, and pass git's own message through verbatim. **`git-ops.ts` was a whole branch menu — list/switch/create/fetch/pull/push — and all of it went when sessions became worktrees**: you don't switch branches in a session's checkout (you start another session), push is Ship's job, and fetch only existed to serve those two. What is left is `gitUpdateFromBase`, and the reason it is not called Pull is load-bearing: **a task branch has no upstream, so `git pull` in a worktree fails with `no upstream configured for branch 'agent/foo'`** — verified. It fetches, then fast-forwards when HEAD *is* the default branch (several agents share the main checkout; a merge there is a conflict resolution nobody asked for) and merges `origin/<default>` in otherwise. Merge not rebase, because Ship pushes early and rebasing a pushed branch means a force-push. A conflict is aborted so an agent never finds its checkout mid-merge. `defaultRemoteRef` reads `refs/remotes/origin/HEAD` — **no network**, which is what lets the worktree-creation path use it — falling back to main/master/trunk/develop for repos made with `git init` rather than cloned, where that symref does not exist.

## 2026-07-30 — Cleanup after a merge is a preference, never new git logic. The merge modal's auto-cleanup…

2026-07-30: **Cleanup after a merge is a preference, never new git logic.** The merge modal's auto-cleanup (`SettingsFile.worktrees.autoCleanupOnMerge`, default on, mirrored by the footer checkbox) calls the same `removeWorktree()` the button calls — unforced `git worktree remove` + `branch -d`. Keep it that way: the safety is that **git refuses**, not that we checked first, so anything tempted to add `--force`/`-D` here is removing the only guard. Three things that shape the UI and are easy to get wrong if you touch it. (1) A cleanup refusal is **not a merge failure** — the commits are on the target regardless, so it renders in its own `cleanupError` warning banner ("Merged, but the worktree was kept") and never in `error`, which means the merge came apart. (2) On success `onRemove()` unmounts the modal (App drops the worktree record), so the merge handler must **return before touching state** rather than falling through to `setBusy`/`refresh` on a dead component. (3) The checkbox is the consent, so auto-cleanup deliberately does **not** re-prompt; only the manual "Remove worktree…" button confirms. Unrelated trap found next door: `AppSettings`' footer reset ran `onChange(DEFAULT_APPEARANCE)` for every pane that wasn't `agents`, so each new feature pane silently shipped a button that discards the user's theme — it is pane-aware now, and a new pane must extend `reset`/`resetLabel`.

## 2026-08-03 — Three mutating git files now, split by blast radius: `git.ts` (read-only) → `git-ops.ts` (branch/remote) →…

2026-08-03: **Three mutating git files now, split by blast radius: `git.ts` (read-only) → `git-ops.ts` (branch/remote) → `git-ship.ts` (commit + push + `gh pr create`).** Ship is one click with no prompts, so every decision it would ask about is a rule instead: base is the repo's own default branch (`gh repo view --json defaultBranchRef`, never a hardcoded `main`), the message comes from `git-text.ts`, and **shipping from the default branch cuts a branch first** rather than refusing — `git add -A` runs *before* the branch decision on purpose, because `git switch -c` carries the index across, which makes one `git diff --cached` the single source of truth for both the commit message and the generated branch name. Everything is idempotent: a second click pushes onto the PR the first opened (`gh pr list --head`), and a clean tree with nothing ahead says "nothing to ship". Two traps. (1) **`gh` is a Homebrew binary and Electron's PATH is not the login shell's** — the path is resolved once through `/bin/zsh -ilc 'command -v gh'` and then `execFile`d directly, so a PR body full of backticks needs no escaping; running gh *through* a shell would. (2) A failed `gh pr create` is not automatically a failed ship — the push already landed, so it re-checks for an existing PR before reporting an error.

## 2026-08-03 — Agent-written git prose lives in `git-text.ts` and is never allowed to block — but branch names are not…

2026-08-03: **Agent-written git prose lives in `git-text.ts` and is never allowed to block — but branch names are not prose.** Commit messages and PR text go through `runAgentJson` under the new `gitText` `AgentTask` (agent-agnostic, picked in Settings → Agents), each with a 25 s timeout and a **deterministic local fallback**, because a CLI mid-update must never be why a change can't ship. Branch naming was tried this way and **removed**: measured against the real CLI, "test" came back as `{"name":"test"}` — identical to the regex — for a second of latency and a spawn. It is now `src/shared/branch-names.ts` (`slugifyBranch` → `uniqueBranchName` → `branchNameFor`), pure, shared by the renderer and `git-ship.ts`, and it also sanitises: `../../etc/passwd` collapses to `etc-passwd`, never a traversal, since the result is both an argv element and a directory name. **The trap that made this visible: a headless `claude -p` writes a session file keyed on its cwd, and `assignProject` files sessions into the sidebar by that path — so running one in the repo it describes puts a "Name a git branch after this task" row in that project's session list.** Every headless feature therefore pins its cwd *outside* the user's repos (`todo-voice` → `~/.chewo/todos`, notes → the notes root, `git-text` → `~/.chewo/git-text`); Home only lists `s.project === homeDir` exactly, so `~/.chewo/*` shows nowhere. Testing gotcha that cost time: **`vi.fn().mockRejectedValue` / `mockImplementation(async () => { throw })` reports a rejection these functions deliberately swallow as an *unhandled* one**, failing the test after its assertions passed — mock the runner with a plain mutable `let answer: () => Promise<unknown>` instead of a `vi.fn()`.

## 2026-08-03 — A worktree per agent session is cheap here, and `node_modules` is the only part that isn't free. Measured on…

2026-08-03: **A worktree per agent session is cheap here, and `node_modules` is the only part that isn't free.** Measured on this repo: `git worktree add` is **0.08 s** (194 tracked files, `.git` is shared so there is no second 179 MB), and `cp -cRp node_modules` is **8.2 s for 0 MB of real disk** — `-c` is an APFS clone, so it is copy-on-write and syscall-bound on ~30k files rather than on the 667 MB. `cloneNodeModules` in `worktrees.ts` runs **fire-and-forget** from the `worktree:create` handler: the pane opens the instant the checkout exists and the dependencies land while the user is still typing, which works because an agent reads code for several seconds before it runs anything. `-p` is load-bearing beyond timestamps — it preserves the **exec bit**, so a cloned `node_modules` sidesteps the npm-strips-`spawn-helper` trap that the root `postinstall` exists to repair. Failure is non-fatal by design (no `node_modules`, non-APFS volume): it toasts and the agent runs `npm install` like it would have anyway.

## 2026-08-03 — Merging into the local main checkout is gone — Ship is the only way work lands, and it goes through a review.…

2026-08-03: **Merging into the local main checkout is gone — Ship is the only way work lands, and it goes through a review.** `mergeWorktree`, `worktreeStatus`, `landingBranchFor`, their IPC, `WorktreeMergeModal`, the `autoCleanupOnMerge` setting and the whole Settings → Worktrees tab were all deleted. Why: it bypassed review, it **never pushed** (so local main silently drifted from origin, which the origin-based worktree cutting then propagated to every new session), and its cleanup checkbox was a second mechanism for the job the merged-PR reaper already does. `worktreeState`'s "this branch is spent" detection stays — git still has to recognise a landed branch however it landed, and the test harness now lands one with a plain `git merge` rather than through the app. **`ShipModal` replaced it**, reached from the tab-bar Ship button (the focused checkout) — and, **until 2026-08-03, also from the sidebar worktree row**; that second entry point is gone as a duplicate, since clicking the row opens the branch and the tab bar's button then covers it. The per-tab icon went the same way earlier, for the same reason: clicking a tab focuses it. It keeps "Mark as done" and "Remove worktree…" in its footer. Two rules hold it together. (1) **`shipPreview` has no side effects** — it must not stage, commit or push, because it is what you read before agreeing; the cost is that its commit message is written from `git diff HEAD` plus untracked *names* rather than a staged diff, which is the right trade against leaving a cancelled review's changes staged. (2) The agent is asked **in the preview**, and `shipPullRequest` takes the confirmed `message`/`pr` as arguments, so pressing Ship is one commit, one push, one `gh pr create` with no model call in between. (3) **The wait lives on the Ship button, not in the dialog** — App reads the preview first and mounts `ShipModal` only with a finished one, because a modal that opens onto "Reading the change…" is a modal that opened too early. The read itself was the real problem: `gh repo view`, `gh pr list` and `git status` now run concurrently, and **a branch with no prior commits skips the PR-text call entirely** (its PR title *is* the one commit's subject, so asking a model to paraphrase text we already have was a second CLI spawn for nothing) — which is the common case, since every session cuts a fresh worktree. `git status --porcelain -uall` is used here deliberately (the panel's `-unormal` collapses an untracked directory to one row, which hides how much is about to be committed — the opposite of what a review needs).

## 2026-08-03 — Isolation is cut on the first message, not at spawn — and merged worktrees reap themselves. (Default flipped…

2026-08-03: **Isolation is cut on the first message, not at spawn — and merged worktrees reap themselves.** (Default flipped to `'current'` on 2026-08-07 — see the first entry; the timing below is unchanged for a session that *is* isolated.) When `TerminalTab.branchMode` is `'separate'`, nothing is created at spawn: the worktree is named after the task, and there is nothing to name it until the user has spoken. `ChatPane`'s `beforeFirstSend` hands that first message to App, which slugs a name, cuts the worktree and **replaces the pane in place** (`replacePane`) with one whose `initialPrompt` is that same text. Four things this depends on. (1) The choice is offered **only until `sessionId` exists** — the honest "this session has started" signal for a chat pane, since the CLI only announces itself on the first turn; moving a live agent between checkouts is a different, manual act. (2) `beforeFirstSend` returning true is a promise to handle the message, so **both** outcomes end in a replacement pane — a worktree that can't be cut lands the session back in the main checkout with the reason in a toast, and no typed message is ever dropped. (3) Both Claude and Codex remain chat panes after the first send; a pty is only an explicit fallback. (4) `cutWorktree` is the only thing that mints a `Worktree`, shared by the create modal and this path. Reaping (`reapMerged`) runs on window focus, throttled to 5 minutes, off **one** batched `gh pr list --state merged --json headRefName` per project — a call per worktree would tax every focus. Three rules make it safe to let it delete checkouts: it calls the same unforced `removeWorktree` (so **git refuses** anything unmerged or dirty), it **never touches a worktree with a live pane** (removal kills panes, and a checkout vanishing under a running agent is worse than an extra folder), and `mergedBranches` returns `[]` when gh is unreachable, so a network failure reaps nothing rather than everything. The throttle stamp is set only once there is something to ask about — worktrees load a beat after first render, and an empty first pass would otherwise spend the window.

## 2026-08-03 — An unstarted isolated pane must not wear the shared checkout's branch. It has no checkout of its own until…

2026-08-03: **An unstarted isolated pane must not wear the shared checkout's branch.** It has no checkout of its own until its first message, so it sits in the project's main checkout — and that checkout is on whatever branch you last left it on, which is *not* this session's. Reporting it made every new session look like it had inherited an old branch (the bug that prompted all of this). `pendingBase` in App drives a dashed `.branch-chip--pending` reading "new branch · from origin/main" instead, and **Update and Ship are hidden** while it is set: both would act on a checkout the pane is only borrowing. What is deliberately *not* done is switching the shared checkout to the default branch — dev servers, the play button and every other pane are standing on it, and it fails outright when dirty. The file tree and git panel do still show that checkout's files; that is honest, since it is what is on disk there. Selecting a project also runs `gitFetchRemote` (throttled 5 min per path, fire-and-forget) — a session is cut from `origin/<default>`, so "start current" is exactly a fetch and nothing that moves a ref any checkout stands on. `git:default-base` names the base for the UI and costs nothing (local symref).

## 2026-08-03 — A branch cut from a remote-tracking ref inherits *that* branch as its upstream, which is what broke Ship.…

2026-08-03: **A branch cut from a remote-tracking ref inherits *that* branch as its upstream, which is what broke Ship.** `git worktree add -b agent/foo <dir> origin/main` leaves `branch.agent/foo.merge = refs/heads/main` (git's default `autoSetupMerge` fires on a remote-tracking start point), so `git status` in the session reports against a branch it is not, and Ship's bare `git push` dies with **"fatal: The upstream branch of your current branch does not match the name of your current branch"** — on *every* worktree session, after the commit had already landed. Two-sided fix, and both sides are load-bearing. (1) `createWorktree` passes **`--no-track`**, so a task branch genuinely has no upstream until Ship gives it one — which is what the comments in `BranchChip.tsx` and `git-ops.ts` had been asserting all along, and were wrong about. (2) `git-ship.ts` no longer treats "`@{u}` resolves" as "this branch has *its own* upstream": `tracksOwnBranch` compares `branch.<name>.merge` against `refs/heads/<name>`, and anything else falls through to `push --set-upstream`, which both pushes and repoints. That second half is not belt-and-braces — it is what repairs the worktrees created before the fix, so no migration was needed.

## 2026-08-06 — Ship can name a branch well because it names it *last*, and commit bodies are no longer hard-wrapped. Two…

2026-08-06: **Ship can name a branch well because it names it *last*, and commit bodies are no longer hard-wrapped.** Two things about the generated text. (1) A session start has only the sentence you typed, so `branchNameFor` slugs it flat — but by the time you ship, a model has read the actual diff and written a conventional-commit subject, so `branchNameFromSubject` (`shared/branch-names.ts`, pure and tested) turns `feat: add oauth callback` into `feat/add-oauth-callback` for **zero extra CLI calls**: the subject was already generated for the commit. The type becomes the prefix; a scope is dropped, because `feat/api/…` reads as a directory; a subject with nothing sluggable after the type falls back to slugging the whole thing rather than emitting a bare `feat/`. It was **offered, never applied** — an existing branch got a "use …" button on the theory that its name may be one somebody is depending on. **Reversed 2026-08-09: it is applied.** Nothing can be depending on that name, because `canName` is already false the moment the branch is pushed or has a PR — and the name it overwrites is `agent/<slug of the first sentence you typed>`, which is exactly the meaningless string the ship-time name exists to improve on, so a button to opt into the better one was a click charged for nothing. The field is now derived (`branchOverride: string | null` in `ShipModal`, `null` = follow the subject) rather than seeded once, so editing the commit message renames with it; typing in the field pins it. Two edges the derivation has to keep: a subject that slugs to nothing leaves an existing branch its name but falls through **empty** when cutting, since `git-ship.ts` names a cut branch from the commit it is about to make and a fallback of `preview.branch` there would mean `git switch -c main`; and the suggestion can now collide with an existing local branch without anyone having asked for it, which main refuses by name ("A branch named X already exists.") and the editable field is the way out. (2) `commitPrompt` used to ask for a body "wrapped at 72 columns" — verified against the real CLI on 2026-08-06, that produced mid-sentence newlines (`came from\nthe task slug`), which is a `git log` convention that predates editing the message in a text box: the field soft-wraps text that is already hard-wrapped, so it reads ragged and one edited word leaves the paragraph re-flowed by hand or not at all. The prompt now asks for whole paragraphs, and `unwrapBody` re-joins them anyway — ten million wrapped commits in the training data are hard to argue a model out of. It inspects each block rather than joining blindly, so bullets, numbered lists, quotes, headings and indented code keep the newlines they need; blank lines are real structure and survive. Re-probed against CLI 2.1.220 after the change: paragraph breaks only. The **PR body is deliberately left wrapped or not as it comes** — it is markdown that GitHub renders, and it is not editable in the modal.

## 2026-08-06 — Ship's route is editable — you can name the branch and pick the target — and "one click, no prompts" survives…

2026-08-06: **Ship's route is editable — you can name the branch and pick the target — and "one click, no prompts" survives because both are answered in the review, not asked at the button.** Ship still takes zero decisions of its own; `ShipModal` just has two more confirmed values to hand it. Four rules, three of which are about not breaking the house rules to get here. (1) **Renaming is refused once the branch is pushed.** `git branch -m` is a local ref move, but the remote keeps the old name and any PR hangs off it, so "renaming" a pushed branch means deleting a remote branch — the `--force`/`-D` territory `git-ship.ts` exists to stay out of. Main refuses it (`isPushed`) rather than trusting the UI to hide the field. (2) **`willBranch` overrides that**, and must: shipping from `main` means HEAD is a branch that is obviously pushed, but nothing is being renamed — the same field names the branch about to be *cut*, which is where naming matters most. Getting this backwards hides the input in the one case it earns its place. (3) **`protectedHead` is now `branch === base || branch === repoDefault`**, not just `branch === base`: retargeting at `develop` while standing on `main` must still cut a branch, and a PR from a branch into itself is not a thing. `branchedFrom` therefore reports the branch we were standing on, not the base. (4) **Retargeting does not re-ask the model.** The commit message describes the working tree and is base-independent; only the commit *range* moves, so `shipCompare` is a bare local `git log` and everything typed survives the change. Bases come from remote-tracking refs, never local ones — a base has to exist on the remote or `gh` rejects it. Two smaller traps: `check-ref-format --branch` **expands** `@{-1}` and reads `-f` as a flag, so both are guarded by hand *before* it (tested in `tests/git-ship.test.ts`, which covers only the pure-git parts — everything else in the file gates on `gh auth status` and would test the developer's own session); and a rename has to be written back onto the `Worktree` record in `onShipped`, because that name is what the sidebar polls state with and what `reapMerged` matches on. The worktree *folder* keeps its task name and is deliberately not moved — it lives under `~/.chewo` and nothing reads it as the branch.

## 2026-08-06 — A fresh worktree now arrives with its `.env` — and "only what git already ignores" is the entire safety…

2026-08-06: **A fresh worktree now arrives with its `.env` — and "only what git already ignores" is the entire safety argument.** SPEC §10.4 rejected auto-copying gitignored files as a secret-leak risk, with the setup command as the alternative; that was written when isolation was opt-in, and once every session cut a worktree it became a per-project tax paid before the first useful session. `copyLocalFiles` in `worktrees.ts` reverses it. Four things hold it together. (1) **Candidates are only the main checkout's *ignored* files** (`git ls-files --others --ignored --exclude-standard --directory`), never a directory walk and never an un-ignored file however the patterns are written: `.gitignore` is tracked, so it travels with the checkout and anything copied stays ignored *there* too — which is what makes it impossible for Ship's `git add -A` to stage a secret this put down. Copying an un-ignored file would instead hand Ship an untracked file to commit that the agent never wrote. `--directory` is load-bearing: it collapses a wholly-ignored folder to one entry, so `node_modules` is one row rather than thirty thousand. (2) It is **awaited** before the pane opens, unlike `cloneNodeModules`' fire-and-forget clone — these are a handful of small files, and an agent that starts against a missing `.env` reads a broken config once and then reasons from it for the rest of the session. (3) Patterns are gitignore-flavoured and live in `shared/local-files.ts` (pure, tested): no `/` matches the **basename at any depth** so `.env` finds `apps/web/.env`, `*` stops at a separator and `**` crosses it, and **last match wins** — which is the only reason the defaults can say "every `.env.*` except the committed examples" in five lines. (4) `node_modules`/`.git` are refused unconditionally and the copy is capped at 100 entries, so a `*` pattern is a bad setting rather than a disk copy. Separately, confirming what the settings pane implies: **the worktree setup command does run on the automatic path** — `startChosenSession` passes `project.worktreeSetup` into the replacement pane and both runtimes chain it (`buildCommand` → `(setup) && agent`, `createChat` → `{ setup } 1>&2 && exec claude`), so a failed setup never silently launches the agent. Its placeholder no longer suggests `cp .env .`, since that job is now done for it — and it never should have suggested `npm install` either: **the pane opens while `cloneNodeModules` is still running**, so a setup command that installs would spend those 8 seconds writing the same `node_modules` tree `cp -cRp` is filling in. Nothing in the app has ever run `npm install` (all three mentions in the tree are comments), so the collision was latent — reachable only by typing it into that field, which the placeholder invited. The clone is **atomic** now rather than incremental: it copies to a sibling of the worktree (same volume, so the rename is atomic; outside the checkout, so `git status` and Ship never see a half-copied folder) and renames into place at the end, discarding its own work if something else got there first. What actually belongs in a setup command is a *side effect a file copy cannot produce* — `direnv allow` (its allowlist is keyed on the directory path, so a new worktree is never trusted), a venv (copied shebangs point back at the main checkout), a per-branch database — never a file, which is what the copy patterns are for.

## 2026-08-04 — Every isolated branch can be deleted from the sidebar, and abandoning one is the single place `--force`/`-D`…

2026-08-04: **Every isolated branch can be deleted from the sidebar, and abandoning one is the single place `--force`/`-D` are allowed.** The trash button used to appear only on a **spent** row (merged/gone/no-branch/marked-done), which meant the one case people actually have — "I started this, I've changed my mind, get rid of it" — had no button at all, and the unforced `removeWorktree` would have refused it anyway: an abandoned branch is by definition dirty or unmerged, so "git refuses" stops being a safety net and becomes a dead end. `removeWorktree(projectPath, worktreePath, branch, discard = false)` now takes a `discard` flag that switches `worktree remove` → `--force` and `branch -d` → `-D`. **The default stays unforced and every automatic caller leaves it alone** (`reapMerged`, cleanup after a ship) — the rule is not "forcing is fine now", it is that forcing requires a person who was shown the loss. What shows them is the row's already-polled `WorktreeState`: `WorktreeRow` hands its `state` up through `onRemove(wt, state)` and `confirmRemoveWorktree` names the exact counts ("throw away 3 uncommitted files and 2 commits not on main"), passing `discard` only when there is something to throw away. Three things worth keeping. (1) That state is **polled, not live**, so an agent can write a file between the poll and the click and git refuses a removal the dialog promised was clean — the refusal is re-asked as the discard question rather than toasted, which is also how the ShipModal footer's "Remove worktree…" works (it has no state, so it passes `null` and always takes the unforced-then-escalate path). (2) The button is safe to show on live rows because `.row__trailing` is **hover/focus-revealed** already — no new CSS was needed, and the same rule is why the dirty-count badge beside it is also hover-only. (3) `git worktree remove --force` once handles a dirty checkout; twice is only for a *locked* one, which we never create, so a lock surfaces as an error instead.

## 2026-08-07 — An isolated session's start point is a picker now, and "the default" is deliberately not stored as a ref. The…

2026-08-07: **An isolated session's start point is a picker now, and "the default" is deliberately not stored as a ref.** The setup row's switch used to state `Its own branch, from origin/main` as a fact; the composer chip is now three controls in one pill (label, `Select`, switch) and the base is `TerminalTab.baseBranch`, passed straight to the `cutWorktree` call in `startChosenSession`. Four things hold it together. (1) **Absent means default, and default is not `origin/main`** — leaving the field alone runs `createWorktree(base: undefined)`, which fetches and then prefers whichever of `origin/<default>` and its local twin is ahead (`freshestBase`), and that resolution only makes sense at cut time. So the picker's first row has value `''`, the ref it resolves to is filtered out of the branch lists rather than offered twice under one name, and choosing it *clears* the field — which is why `setPaneChoice` builds its patch key by key instead of dropping every `undefined`: `baseBranch: undefined` has to reach the spread to clear it. (2) The list is `listBranches` (a local `for-each-ref`, no network), cached per project path in `branchLists` and re-read on every project selection — a branch created in a terminal a minute ago has to be offerable without a restart — plus an on-demand read for any project with a pending pane, since a pending pane need not belong to the selected project. A failed read is not surfaced: the picker keeps the default row, which is what it would have used anyway. 2026-08-09: **Discarding a change is the fourth mutating git file, and the confirmation is the entire safety mechanism.** `src/main/git-discard.ts` joins the blast-radius split (`git-ops.ts` brings commits in, `git-ship.ts` sends work out, `worktrees.ts` manages checkouts, this destroys uncommitted work); `git.ts` stays read-only, and `safePathspec` is now exported from it because these strings reach commands that delete files — it also rejects a leading `-` now, which a read did not need. `git clean -f` is a force flag and it is allowed here for the same reason `removeWorktree(discard)` allows `--force`/`-D`: a person was shown the loss and asked anyway.
